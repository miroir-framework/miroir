# 284 — Adversarial review of the OpenAPI connection wizard analysis

> Attack of `analysis.md` (issue #284) against the current Miroir codebase. Design *choices* (D1–D23) are not relitigated; feasibility, internal consistency, citation accuracy, missing call sites, and unsatisfiable mechanisms are.

**Verdict.** The analysis matches today’s linear multistep host, external-service client, sync transformer, secrets, and home-report citations well enough to justify the gap narrative. It is **not implementation-ready as written**: D14’s step count disagrees with §5.1, branching conflicts with `allGatedStepsAllowFinish` and index-based Back/Next, D5-a understates schema and renderer blast radius, §5.2 misplaces the validation report and omits how `connectExternalService` is registered and run, D17 contradicts the cited Spotify report’s URL-param naming, and D6/D15 assume on-Next server work, dynamic input schemas, and file upload without naming host or section call sites. Secret redaction targets exist (`redactRegisteredSecretValuesInString`) but Finish logging paths in `DomainController` and `runMultistepFinish` are wider than §3.2 alone admits.

**Dispositions (all 17 applied in analysis.md):** R1 → D14 and §5.1 twelve step ids, subset visited. R2 → Finish gate is `visitedStepIds` only. R3 → new `handleAction` arm, not `libraryImplementation`. R4 → report `conceptLevel: "Model"`, model section. R5 → Spotify report is a structural template. Wizard uses OpenAPI parameter names. R6 → list child union `reportSection | multistepStep`, renderer inventory. R7 → host evaluates `inputSchemaFromBag` on step open. R8 → Next sequence: gate, onNext, merge, branch. R9 → `visitedStepIds` stack. R10 → `unwrapAction2ErrorMessage` for Next and Finish. R11 → log and DOM sites listed in §5.4. R12 → browser `FileReader` into `document.text`. R13 → `listConvertibleGetOperations` / `boundPathsForOperation`. R14 → target model via the bag uuid and `applicationDeploymentMap`. R15 → snapshot plus `unregisterProcessSecret`. R16 → D11 mapping table. R17 → required fields on the resolved operations schema.

## Recommendations

- [x] **R1** [blocker] — D14 “ten steps” vs §5.1 walk table: D14 and the issue body say ten steps; §5.1 lists twelve `stepId`s (`application` … `review`), and the auth branch adds three mutually exclusive secret steps on top of shared steps (`authenticated`, `scheme`, `operations`, …). → Reconcile D14, §5.1, and acceptance copy: either count only user-visible “screens” with an explicit rule for branched secret steps, or update D14 to twelve list children and document minimum/maximum host indices visited per path.

- [x] **R2** [blocker] — Branching vs Finish gate `allGatedStepsAllowFinish`: Finish calls `steps.every(… currentStepAllowsNext …)` over **all** list children (`MultistepReportHost.tsx:170–191`, `:403–405`), and #274 tests encode that as intentional (`multistep.274.phase0.unit.test.ts:337–375`). A wizard list that includes `secretsAuthCode`, `secretsClient`, and `secretsCustom` will fail Finish when the user only filled one branch unless skipped steps are empty optional bags by construction. → In D5/D15 and §5.1, require either (a) Finish validates only the **visited** step-id path (new API), or (b) branched steps are removed from the static list and injected at runtime, or (c) non-taken secret steps are non–input-report sections with no bag keys. Do not assume index paging alone skips validation.

- [x] **R3** [blocker] — `connectExternalService` wiring unspecified: No `connectExternalService` symbol exists in the repo; Finish today is only `compositeActionSequence` → `handleCompositeActionTemplate` → `handleAction` for known `DomainAction` arms (`DomainController.ts:4785–4984`). A monolithic probe+upsert handler must be registered (Endpoint **Action** row with `libraryImplementation`, new `domainAction` / composite template arm, or explicit sequence of `secrets.set` + `updateInstance`/`createInstance` documented per payload shape). → Add §5.2 subsection: action endpoint uuid, `actionType`, parameter schema (bag → handler), Admin vs target `application` on each sub-call, and how `handleAction` / `handleApplicationAction` resolves the target app from the bag (`DomainController.ts:3008–3050`).

- [x] **R4** [major] — Validation report section contradicts cited Spotify shape: §5.2 step 5 upserts “the report on the target application’s **data** section”; the acceptance template `10ce3252-….json` lives under `spotify_model/` with `"conceptLevel": "Model"`. Multistep fixture `d2b2fbbd-…` is also under `library_model/`. → Normatively set `applicationSection: "model"` (and `conceptLevel: "Model"`) for generated probe reports unless the analysis documents a deliberate departure from Spotify/Library precedents.

- [x] **R5** [major] — D17 vs §3.6 Spotify report URL params: D17 requires OpenAPI parameter names in the input section and `urlParamFields`; `10ce3252-….json` uses `playlistId` in `urlParamFields` and `inputMLSchema`, while the extractor binding uses OpenAPI name `playlist_id` with `referenceName: "playlistId"`. “Finish copies” the section **shape** (input + `apiCallReportSection`) but not D17 naming. → In §3.6/D17, state explicitly that Spotify’s report is a structural template only and that wizard output renames URL params to OpenAPI names (breaking Spotify’s `playlistId` alias pattern).

- [x] **R6** [major] — D5-a envelope schema location: `listReportSection.definition` array items are **`reportSection` refs only** (`3f2baa83-….json:161–169`), not the top-level `reportSection` union. An envelope is a **sibling** type on the list’s child union plus dual-write on EntityVersion `952d2c65-…`. → Replace “list schema union grows one member” with “list child union = `reportSection | multistepStepEnvelope`”, and inventory non-host renderers (`ReportSectionListDisplay.tsx`, `ReportTools.ts` `reportSectionsFormSchema` / `reportSectionsFormValue`, designer JSON dialogs) that must unwrap or reject envelopes.

- [x] **R7** [major] — `inputSchemaFromBag` has no render call site: `ReportSectionViewWithEditor.tsx:738–747` passes static `definition.inputMLSchema` into `ReportInputSection`; the host never evaluates a bag transformer at step open. D15’s dynamic Jzod for `operations` / `probeParams` cannot work without host → context → editor plumbing (and a rule for bag keys when `inputMLSchema` is omitted in JSON, per D5-a). → Specify evaluation point (host on `stepIndex` change), transformer inputs, caching, and how `collectStepBagKeys` / `currentStepAllowsNext` use the **resolved** schema.

- [x] **R8** [major] — On-Next server actions vs `handleNext`: `handleNext` only bumps `stepIndex` after client-side `currentStepAllowsNext` (`MultistepReportHost.tsx:365–381`); there is no DomainController call on Next. Document-step parse/fetch (§5.1 `document`, D6/D15) and probe-less bag merges require a new async Next path, error surface (D15 “stay on step”), and distinction from `multistep-step-query-failure` (report **query** failure in `ReportViewWithEditor.tsx:541–544`, not action failure). → Add §3.2/§5.4 host sequence diagram: Next → optional `onNext` action → merge bag → optional `branch.test` → navigate by step id; Finish unchanged.

- [x] **R9** [major] — Back on path taken vs `stepIndex - 1`: `handleBack` is `Math.max(0, stepIndex - 1)` (`MultistepReportHost.tsx:360–363`). Branching (D5, acceptance “Back follows the path taken”) needs a **stack** of visited step ids, especially when `whenFalse`/`whenTrue` rejoin or skip indices. → Document required host state (`visitedStepIds[]`) and interaction with envelope-only steps; do not claim #274 already provides this.

- [x] **R10** [major] — Inner error messages vs composite wrapper: Finish sets `result.errorMessage` only (`MultistepReportHost.tsx:420–422`); composite failures wrap as `"handleCompositeActionTemplate compositeInstanceAction error"` (`DomainController.ts:5007–5014`) while the probe/parser message sits in `Action2Error.innerError` (`DomainElement.ts:216–217`). D15/§5.4 require the innermost message for Next and Finish. → Require `unwrapAction2ErrorMessage(error)` at host (and for on-Next failures) and add a regression test; note Next-action failures must not use the Finish-only path.

- [x] **R11** [major] — Secret leakage paths wider than §3.2/§5.4: Besides `runMultistepFinish` logging the full `sequence` (`MultistepReportHost.tsx:63–69`) and the visible `<pre data-testid="multistep-step-bag">` (`:461–463`), `handleCompositeActionTemplate` logs `localActionParams` and per-step `localContext` (`DomainController.ts:4795–4803`, `:4846–4855`, `:4992–4998`). `SecretStore.redactRegisteredSecretValuesInString` exists (`SecretStore.ts:69–84`) but is not used on those paths. → List every log/DOM site in §5.4 and mandate redaction or structured logging without bag/sequence bodies; gate debug JSON in `ReportViewWithEditor` (`:517–520`) under multistep + secrets.

- [x] **R12** [major] — D6 browser upload mechanism missing: No report-section type reads a file into the step bag; upload elsewhere is ad hoc (`BlobEditorField.tsx`, `Importer.tsx`). Paste fits `inputReportSection`; URL fits on-Next server fetch (R8). → Name the wizard UI for upload (custom section vs masked string vs one-shot action) and where bytes enter the bag before `openApiDocument` is set.

- [x] **R13** [major] — §5.3 bound-path walk is greenfield: `syncExternalServiceSchema` only converts with pre-supplied `operationSync.<id>.boundPaths` (`syncExternalServiceSchema.ts:539–545`); it does not enumerate “convertible GET fields” or skip `oneOf`/`anyOf` for the checklist. D7/D16 require a new walker (likely sharing `convertSchema` / `deref` internals). → Add §5.3 export or module boundary (`listConvertibleGetOperations(doc)` / `boundPathsForOperation(doc, id, rule)`) and clarify whether the document step’s “convertible operation list” reuses the same code as Finish.

- [x] **R14** [major] — Target-application model for clash check and upsert: The wizard report runs under Miroir (`HomePage.tsx:73–75`, §5.1 `360fcf1f-…`); Finish passes `props.application` into `runMultistepFinish` (`MultistepReportHost.tsx:412–418`) but persistence must use the bag’s target app (step `application`). Name clash (D18) needs endpoints from the **target** deployment model, not only `useCurrentModelEnvironment` for Miroir. → §5.2 step 1/6: load target `MetaModel.endpoints` (or store read) by bag uuid + map; document cross-app `applicationDeploymentMap` entries (D22) required in tests.

- [x] **R15** [minor] — D13 process-map restore API: `registerHydratedProcessSecret` overwrites (`SecretStore.ts:27–29`); there is no delete/restore helper for probe rollback. Feasible inside `miroir-core` but not “call existing restore”. → One sentence in §D9/D13: snapshot prior `resolveSecret` outcomes per name, restore via re-register or new `unregisterProcessSecret`.

- [x] **R16** [minor] — Custom token vs `http` scheme typing: D11 adds `authorizationTemplate` on `http` and `{ type: "none" }`; D3 “custom Authorization template” must map to `securityScheme: { type: "http", … }` + `credentialKey` + template, distinct from `none` (Discogs public vs token runs). → Add a small mapping table in §D11/§5.2 so Finish does not emit invalid `EndpointSecurityScheme` objects.

- [x] **R17** [minor] — Operations-step validation: “at least one checked, probe ∈ checked” (§5.1) is not expressible with today’s `currentStepAllowsNext` (only required fields on static `inputMLSchema`, `MultistepReportHost.tsx:254–261`). → Extend gated-step logic for bag-driven checklist steps or encode constraints in the resolved dynamic schema with required arrays.

## What the analysis got right (so it is not all wreckage)

- Linear multistep characterization (#274): index paging, single Finish composite, step bag in React state, cancel copy staleness, and composite error wrapping match `MultistepReportHost.tsx` and `DomainController.ts`.
- External call constraints: GET-only, `enabledOperations`, HTTPS / private host rules, Bearer-only Authorization today, lenient probe validation — align with `ExternalServiceClient.ts`.
- Sync alignment: stored document text (no URL fetch in sync button), non-GET skip, `boundPaths` required, `oneOf`/`anyOf` bounded conversion throws — align with `syncExternalServiceSchema.ts` and `OpenApiEndpointSyncButton.tsx`.
- Home launcher anchor: `MiroirWebAppOrDesktopHome` section inventory, Library `selfApplication` on the JSON row vs URL `homePageUrl.selfApplication`, default deployment map keys, and `openReportSection` type — accurate.
- Identity story: derived endpoint uuid v5 vs hand-built `0e5cb172-…`, secret uuid helper, and refusal to adopt the legacy Spotify endpoint uuid — arithmetically verified.
- Report union size (16 members including `apiCallReportSection` and `openReportSection`) and dual-write entity uuids — match present-model JSON and generated types.
- Prerequisites (#267/#270/#274/#281) and rejection of client-assembled Finish composites (Proposal 2) — consistent with logging and secret-handling realities.
