# 270 — Adversarial review of persistent named-secrets analysis

> Attack of `analysis.md` (and issue #270) against the current Miroir codebase on branch `270-FEATURE-persistent-named-secrets`. Design *choices* (D1–D9) are not relitigated; feasibility, internal consistency, and factual claims are. Every citation below was walked against the working tree on 2026-09-11.

**Disposition (2026-09-11):** R1–R11 applied in `analysis.md` (principal-scoped OAuth caches; `persistRotatedSecret` callback + `SecretsService`; `handleSecretsHttpRoute` persists through `RestClientStub`; MCP response redaction; composite principal thread; testable startup home; migration/docs; blast radius; `/queryTemplate` hedge removed; citation fixes; guard bypass debt). Product choices D1–D9 unchanged.

**Verdict (at review time).** The fact base is unusually solid: the Admin inventory (9 entities, 8 menu items, 3 credential seeds), the Spotify endpoint, and nearly every file:line citation check out, and the principal-drop diagnosis (§3.5) is real. But the target design is **not implementation-ready** as written, for two structural reasons: (1) D2-b's "thread `AuthPrincipal` into `resolveSecret`" is defeated by the existing OAuth token cache and rotation map, which are keyed by secret **name** and short-circuit resolution entirely — as specified, Carol gets Alice's access token; (2) D7's "encrypt and update the same `MiroirSecret` row" has no channel: the rotation is detected three function-levels deep inside `ExternalServiceClient` (4_services), which has no persistence handle, cannot import `DomainController` (3_controllers) without inverting the layering, and never surfaces the rotated value to any caller. Several majors compound this: the `/secrets` in-process test path is unspecified (the `/auth/*` precedent it cites does **not** persist through `RestClientStub`), D8's "MCP strips like `passwordHash`" is factually false for MCP tool **responses**, and the principal-thread list omits the composite-action path that can also host `extractorFromAction`. Fix R1–R2 in the analysis itself before the TDD plan is written.

Errors: the claim that "`graphify-out/graph.json` is absent in this workspace" is **false** (it exists, with `GRAPH_REPORT.md`; AGENTS.md says to query it first); `server.ts:438-468` should be `:438-471`; the rotation write is `:488` (log at `:490-493`), not `:488-489`; the D6 env map is `:30-35`, not `:29-35`. ## Recommendations

- [x] **R1** [blocker] — D2-b is defeated by the name-keyed OAuth caches; "user-scoped wins" never happens on a warm cache: The analysis's whole per-user mechanism is "thread `AuthPrincipal` into the query path → `resolveSecret(name, principal?)`". But `resolveAuthorizationCodeToken` checks the access-token cache **before** resolving anything, and the cache key is `oauth2AuthorizationCodeCacheKey(scheme)` = `tokenUrl | clientIdKey | refreshTokenKey` — the **names** from the endpoint instance, not the resolved values and not the principal (`ExternalServiceClient.ts:387-389`, cache probe at `:400-404`). The Spotify endpoint's names are fixed (`spotifyClientId` / `spotifyClientSecret` / `spotifyRefreshToken`), so Alice's first call populates `oauth2TokenCache` (`:45`, write at `:496-500`) and Carol's call returns **Alice's cached access token** for up to an hour without `resolveSecret` ever running. Same defect in the rotation map: `rotatedRefreshTokens.get(scheme.refreshTokenKey)` (`:424`) is keyed by name, so Alice's rotated refresh token is used for Carol's refresh, and D7's write-back would then persist Alice's token over Carol's row. The analysis cites `rotatedRefreshTokens` (`:47`) and the write (`:488-489`) but never mentions `oauth2TokenCache` or `oauth2AuthorizationCodeCacheKey` — the two structures that actually decide which user's credential is used. This is not relitigating D2-b; it is D2-b internally inconsistent with the code it must live in. → Specify principal-scoped caching: cache key must include `principal?.miroirUserUuid ?? "process"` (or the resolved refresh-token value hash) in `oauth2TokenCache`, `rotatedRefreshTokens`, and the client-credentials cache (`:292`); the 401-retry path (`:659-675`) must re-resolve with the same principal. Add a test: two principals, same endpoint, distinct tokens, no cross-serving from cache.

- [x] **R2** [blocker] — D7 has no persistence channel, and the obvious one violates the layering: "When the token endpoint returns a new `refresh_token`, encrypt and update the same `MiroirSecret` row" — by whom? The rotation is detected inside `resolveAuthorizationCodeToken` (`ExternalServiceClient.ts:487-493`), a module-level function in **4_services**. It has no `DomainController`, no store handle, no wrapping key, and its only return is the access-token string; `executeExternalServiceOperation`'s `Action2ReturnType` (`:551-555`, `:723`) carries no rotation information, so the caller in `DomainController` never learns a rotation happened. `ExternalServiceClient` cannot import `DomainController` — implementation dependencies flow downward (3_controllers → 4_services), and `DomainController.ts:165` already imports `ExternalServiceClient`, so a reverse import would be a cycle. The analysis's "Key reuse" table lists no mechanism for this, and §5's "Rotation persists (D7)" is a sentence, not a design. Also unspecified: where the wrapping key lives at runtime so the write path (and `/secrets` POST) can re-encrypt — D4 step 7 says "re-encrypt, persist, update the in-memory map" without naming the module that holds the key. → Name the mechanism: either (a) `executeExternalServiceOperation` returns rotation metadata (e.g. `rotatedSecret: { name, scope, miroirUserUuid?, newValue }`) and the `DomainController` call sites (`:3260-3264`, `:3037-3044`) persist via a dedicated-actionLabel `updateInstance`; or (b) inject a `SecretsRepository`-style callback into `ExternalServiceClient` at startup (server.ts / test harness), keeping the layering arrow pointing down. State where the wrapping key is held (module-level service in `miroir-core`, set once at startup, never serialized — same discipline as `processTokenSecret` in `AuthenticationPolicy.ts:157-170`). Also state which row is updated when resolution fell back to process scope (D2 step 2) — "the same row that supplied the token" requires `resolveSecret` to report which scope won; today it returns a bare string (`SecretStore.ts:14-23`).

- [x] **R3** [major] — The `/secrets` routes are unreachable from the test suite as specified, and the cited precedent does not persist: D5 says "keep the routes callable in tests (in-process)". Most tests never start `miroir-server`; they use the emulated in-process server (`RestClientStub`), which dispatches exactly two things: `handleAuthHttpRoute` for `/auth/*` (`RestClientStub.ts:74-91`, policy in `1_core/authentication/AuthenticationHttp.ts:30-91`) and `restServerDefaultHandlers` matched by method+url (`RestClientStub.ts:165-175`). An express-only `app.post("/secrets", …)` in `server.ts` is invisible to every emulated-server test. Worse, the `/auth/change-password` precedent the analysis cites (D5) is **not a persistence precedent in-process**: `handleAuthHttpRoute` returns `{ changed: true, directory }` and the stub merely swaps an in-memory directory (`RestClientStub.ts:81-88`) — only the express route persists via `domainController.handleAction(updateInstance)` (`server.ts:696-717`). If `/secrets` copies that shape, D4's "store is the source of truth" and D7's rotation write-back cannot be integration-tested through the stub at all. `AuthenticationHttp.ts` is missing from the analysis's Key sources. → Specify a process-agnostic `handleSecretsHttpRoute` sibling (miroir-core) wired into **both** `server.ts` and `RestClientStub.call`, and specify that the write path persists through the stub's `serverDomainController` (`RestClientStub.ts:140-142`) with a dedicated `actionLabel` that the extended guard permits (the `AUTH_CHANGE_PASSWORD_ACTION_LABEL` pattern, `AuthenticationPolicy.ts:443`, `server.ts:699`). Say explicitly that the in-process path must persist, departing from the change-password stub behavior.

- [x] **R4** [major] — D8's "MCP strips ciphertext the same way `passwordHash` is stripped" is false for MCP responses: The live redactor is applied to MCP **logs** (`mcpHandlersForEndpoint.ts:215`, `:250`, `:279`) but **not** to MCP tool **responses**: the success payload serializes raw `result.returnedDomainElement` (`mcpHandlersForEndpoint.ts:286-295`) and the error payload serializes raw `errorContext` (`:299-317`). Today an MCP client calling the generated `getInstances` tool with the Admin deployment uuid gets `passwordHash` in the tool response (Admin is always-allow, `AccessPolicy.ts:36-39`; MCP has no auth gate). After #270 the same call returns `MiroirSecret.ciphertext`. §3.6's "Live helper used by REST/MCP/DC" is only true of MCP logging. Extending the helper (parentUuid-keyed `ciphertext` strip) is necessary but not sufficient. → Add a redaction call site on the MCP response path in `mcpHandlersForEndpoint.ts` (both success and error branches) as an explicit work item; record the pre-existing `passwordHash`-via-MCP exposure as fixed-by-this-issue or explicitly deferred.

- [x] **R5** [major] — The principal-thread inventory omits the composite path, which can also host `extractorFromAction`: §5 lists `handleBoxedExtractorOrQueryAction` / `executeBoxedExtractorOrQueryAction` / `resolveExtractorFromActionInBoxedQuery` / `executeExternalServiceOperation` plus `queryActionHandler` and `handleApplicationAction`. Missing: `handleCompositeRunBoxedQueryAction` → `executeCompositeRunBoxedQueryAction` calls `handleBoxedExtractorOrQueryAction` with no principal (`DomainController.ts:4465-4487`, `:4499-4513`), reachable from `handleActionInternal` (`:3521`), from composite action templates (`:3654`, `:3959`, `:4752`), and from MCP composite tools in-process (`Miroir_compositeRunBoxedQueryAction` exists; `mcpHandlersForEndpoint.ts:273` calls `handleAction`). `handleCompositeActionTemplate` itself is invoked from `handleApplicationAction` (`:3130-3137`) — which, per the analysis's own truth table, never receives the principal. So even after the §5 thread is built, a composite action containing a boxed query with `extractorFromAction` resolves process-scoped only, silently ignoring Alice's user-scoped row — a fail-**open** surprise for D2-b's "user-scoped wins when a principal is present". → Extend the thread end-to-end: `handleAction` → `handleApplicationAction` → `handleCompositeActionTemplate` / `handleCompositeAction` → `executeCompositeRunBoxedQueryAction` → `handleBoxedExtractorOrQueryAction`. Either that, or document that composite-hosted external queries are process-scope-only for this issue and add a test pinning the behavior.

- [x] **R6** [major] — The startup orchestration has no testable home: D4's seven-step startup sequence (parse import set → fail closed → encrypt+upsert → load rows → fail closed → decrypt+hydrate) is specified to run in `server.ts`, but `miroir-server` has no test suite: `packages/miroir-server/tests/` contains only `tmp/`, there is no `vitest.config`, and the `"test"` script in `packages/miroir-server/package.json` has no test files to run. #267 already learned this lesson and extracted `parseServerArgs` into `miroir-core` precisely so it could be unit-tested (`packages/miroir-core/tests/4_services/serverSecrets.unit.test.ts`). The analysis does not say where the import/upsert/hydrate/fail-closed logic lives, so the TDD plan will stall or push untested orchestration into `server.ts`. → Specify a `SecretsService` (or `secretsStartup.ts`) in `miroir-core` 4_services: pure functions for import-set assembly (including the D6 AI aliases), encryption/decryption, and a hydrate/import orchestrator taking a minimal persistence interface; `server.ts` shrinks to wiring, exactly the `parseServerArgs` precedent. ## What the analysis got right (so it is not all wreckage)

- **Inventories are exact** (verified programmatically): 9 Admin entities with the cited names+uuids; 8 Admin menu items with the cited reportUuids, Users+Rights carrying `menuItemScope: "data"` and the other six none; 3 credential seeds (`c179dcf9`→alice, `23f39cd9`→carol, `cc3bc0aa`→dave), bob `95fa298f-…` credentialess; zero EntityVersion files under `admin_model/54b9c72f-…`; Spotify endpoint `0e5cb172-…` with `oauth2AuthorizationCode` and the three cited key names + tokenUrl; `a96856df-…` is collision-free.
- **The §3.5 principal diagnosis is the real deal**: `handleAction` takes `principal` last (`DomainController.ts:2915`) and only logs it; `queryActionHandler` calls `handleBoxedExtractorOrQueryAction` with three args (`RestServer.ts:503-507`); `resolveExtractorFromActionInBoxedQuery` calls `executeExternalServiceOperation` principal-less (`DomainController.ts:3260-3264`); `server.ts:576` and `RestClientStub.ts:192` do put `authPrincipal` on params. D2-b genuinely cannot work until this is threaded.
- **The two-redactor warning is correct and important**: the live helper is `4_services/redactCredentialSecrets.ts` (imported by `RestServer.ts:43`, `PersistenceStoreController.ts:54`, `DomainController.ts:166`, `mcpHandlersForEndpoint.ts:17`); the `AuthenticationPolicy.ts:445-463` copy strips only `passwordHash` and is not the REST helper. Extend the live one.
- **The guard-extension strategy is well-anchored**: `assertCredentialInstanceMutationAllowed` (`AuthenticationPolicy.ts:465-497`) fires in `handleInstanceAction` and the CRUD handler, which covers every remotely reachable generic-mutation path today (R11's caveat aside).
- **AiConfiguration facts**: description literally says "API keys are stored as server-side environment variables"; `providerType` enum is `openai|anthropic|google` while the runtime accepts `"github"` (`copilotRuntimeFactory.ts:18`); the entity file is indeed not exported from the admin package `index.ts`.
- **The D3 negative example is real**: `getProcessTokenSecret` (`AuthenticationPolicy.ts:161-170`) generates an `ephemeral-…` secret when unset — reusing it as the wrapping key would brick every row on restart.
- **The MCP/Electron non-goal is consistent with the code**: `miroir-mcp/src` has zero references to `resolveSecret`/`ExternalServiceClient`/`extractorFromAction`, and `listTools` skips external-service endpoints (`EndpointToolRegistry.ts:181-189`); Electron's in-process stack (`ipcServerSetup.ts`) registers no secrets, so external calls fail closed there — the hole is exactly the documented #267 R11 / #263 one, no bigger.
- **Feasible-as-advertised pieces**: Admin store is open early enough for a startup hydrate (`server.ts:346-363`); the `queryExecutionStrategy: "storage"` boxed-query read pattern exists and works at startup (`server.ts:365-389`); `?page=login` dispatcher pattern exists (`PageDispatcher.tsx:142-213`); `resolveSecret`/`registerSecrets`/`clearSecrets` are exported from `miroir-core` (`index.ts:1322-1324`) and `miroir-ai` already depends on `miroir-core`, so D6's `getApiKey → resolveSecret` is a legal import.
