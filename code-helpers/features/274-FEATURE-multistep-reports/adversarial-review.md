# 274 — Adversarial review of Multi-step Reports analysis

> Attack of `analysis.md` (and issue #274) against the current Miroir codebase. Design *choices* (D1–D17) are not relitigated; feasibility, internal consistency, and factual claims are. All counts and line citations were re-verified programmatically or by direct read on 2026-09-13.

**Disposition (parent, 2026-09-13).** R1–R12 applied in `analysis.md`: step bag (not raw Formik); host state above the query-failure unmount; URL writes disabled in multistep; `runStoredQueries` unsupported; `openReport` on list sections for D17; `reportSectionsFormSchema` inventory; seed counts 71 omit + 2 null; dual-write paths; `CompositeActionSequenceTemplate`; Finish `modelEnvironment`; launcher `pageParams`. Checkboxes below are ticked for those repairs.

**Verdict.** The core mechanism is real: `RunnerView` passes its whole Formik `values` as `actionParamValues` into `handleCompositeActionTemplate`, and `DomainController` merges that into the parameter context that `getFromParameters` reads — so "Finish with the Report Formik tree" is a pattern the code already implements, and the pager design (one `reportSectionPath` into `ReportSectionViewWithEditor`) matches the actual component API. But the analysis is **not implementation-ready**: its central dataflow is unspecified where it matters most — "the Report Formik tree" is not a clean parameter bag (it contains the full query results spread, `pageParams`, and the entire Report definition under the report's own name), and the literal Next-merge `{ ...launchPageParams, ...formikValues }` is circular and self-polluting; the analysis itself punts the merge spec to the TDD plan. On top of that: a closed switch in `reportSectionsFormSchema` throws on any new section type, the query-failure branch in `ReportViewWithEditor` unmounts the Formik (destroying the bag the analysis is at pains to protect), URL-writing affordances inside `ReportInputSection` contradict D8/D16 from within a modal, and D17's "list-row launcher" has no rendering mechanism today. The seed-Report inventory count is also wrong in detail (71 absent + 2 explicit `null`, not 73 absent). Fix R1–R6 in the analysis, then write the TDD plan.

## Recommendations

- [x] **R1** [blocker] — "The Report Formik tree" is not the bag; the D5/§5.3 merge is circular and pollutes the parameter namespace: `initialReportSectionsFormValue` is `{ ...reportSectionsData, ...props.storedQueryData, ...reportData, pageParams: props.pageParams, [reportReportDetailsKey]: …, [reportName]: props.reportDefinition }` (`packages/miroir-standalone-app/src/miroir-fwk/4_view/components/Reports/ReportViewWithEditor.tsx:261-269`). Consequences the analysis never mentions:
  1. **Finish payload (D5)** as literally specified passes the *entire Report definition* (under key = the report's `name`, L226/L268), the whole `reportData` query-result spread, and `pageParams` itself into the action parameter namespace. `getFromParameters("pageParams")` returns an object; any query-result key colliding with an `inputPrefix` bucket is read as a parameter.
  2. **Clobbering**: spread order (L262-265) means `storedQueryData` / `reportData` overwrite same-named input buckets in initial values.
  3. **Circular merge (§5.3)**: `{ ...launchPageParams, ...formikValues }` puts a `pageParams` key (and reportData keys, and the report definition) *into* `pageParams`; the host then feeds that back as `props.pageParams`, which rebuilds `initialReportSectionsFormValue` (deps include `props.pageParams` and `reportInterpreterPageParams`, L272), which re-triggers the `enableReinitialize` reset the analysis's own risk table is trying to survive.
  The analysis defers this ("exact merge documented in the TDD plan", §5.3) — but this *is* the feature's central dataflow; deferring it is deferring the design. → Specify in the analysis: (a) the exact key set passed to Finish and merged on Next/Back (presumably only `inputPrefix` buckets + hoisted object-instance keys, with everything else stripped); (b) collision rules between bucket names and `reportData` keys; (c) the reinit-safety mechanism (e.g. bag held in host state outside the Formik `initialValues` dependency chain, or a custom `enableReinitialize`-guarding merge), not just the aspiration "keep collected keys" (D8 rule 1).

- [x] **R2** [major] — Closed switch: `reportSectionsFormSchema` **throws** on any section type it does not know; the new `openReportSection` will crash the Add/Edit dialog: The switch handles only `list` / `grid` / `objectInstanceReportSection`; `objectListReportSection`, `markdownReportSection`, `modelDiagramReportSection`, `graphReportSection` and the `default` branch all `throw new Error("reportSectionsFormSchema: report section type … is not supported")` (`packages/miroir-standalone-app/src/miroir-fwk/4_view/components/Reports/ReportTools.ts:104-113`). Its only caller is `JsonObjectEditFormDialog` on `(defaultDetailsReport)?.definition?.section?.definition[0]` (`packages/miroir-standalone-app/src/miroir-fwk/4_view/components/JsonObjectEditFormDialog.tsx:300-312`). Any entity whose details report's first section is an `openReportSection` (or, today already, an `inputReportSection` — also unhandled) crashes instance editing with that throw. Note the asymmetry: `reportSectionsFormValue`'s `default` returns `{}` (`ReportTools.ts:250-260`) and is safe. → The analysis's §5.5 / risk table must inventory the section-type switches and add `case "openReportSection": return {}` (or a real schema) to `reportSectionsFormSchema`; state explicitly that `ReportSectionViewWithEditor` has *no* default branch — unknown types render nothing silently (`ReportSectionViewWithEditor.tsx:367-620` is a bare `&&` chain) — so the D14 renderer is additive, not a break, but the form-schema switch is a hard break.

- [x] **R3** [major] — Modal/multistep host must neutralize the URL-writing affordances inside `ReportInputSection`, or D8/D16 are violated from within the dialog: `ReportInputSection` (a) renders an OK/Apply button whenever `urlParamFields` is set, whose handler does `navigate("/?" + next.toString())` with the input values (`packages/miroir-standalone-app/src/miroir-fwk/4_view/components/Reports/ReportInputSection.tsx:81-92`, button at L113-122), and (b) navigates on `application` field change (`buildReportApplicationSwitchUrl` → `navigate`, L55-70). Inside a `ThemedDialog` modal (D6/D14) there is no report URL of its own — these navigate the *underlying page route* behind the modal and write step values into the page search string, contradicting "we still do not use the URL for step values" (D8) and "no `step=N`" (D16), and in route-host mode they bypass the in-memory merge entirely. The analysis acknowledges the URL bridge exists but never says the multistep host disables or reroutes it. → Specify: in multistep mode (or at least modal mode), `urlParamFields` Apply and the application-switch navigation are disabled / redirected into the host's in-memory param merge; state what happens to `reportHasUrlParamInputSection`-driven UI (`ReportViewWithEditor.tsx:205-220,416-421`) on a multistep report.

- [x] **R4** [major] — D17's "list-row launcher" has no mechanism: `openReportSection` is a *section*, rendered once per report page; list rows are table cells: `objectListReportSection` rows render through `EntityInstanceGrid`, whose per-row affordances are exactly: tools-column edit/delete (`packages/miroir-standalone-app/src/miroir-fwk/4_view/components/Grids/EntityInstanceGrid.tsx:546,1146-1147`) and cell-click navigation to the row entity's `defaultInstanceDetailsReportUuid` with the row PK in the URL (L790-857, FK columns L820-841). ## What the analysis got right (so it is not all wreckage)

- **The central mechanism is real.** `RunnerView` passes the whole Formik `values` as `actionParamValues` to `domainController.handleCompositeAction` / `handleCompositeActionTemplate` (`RunnerView.tsx:597-603,613-619`); `handleCompositeActionTemplate` (`DomainController.ts:4696`) builds `localActionParams = { ...templateEvaluationParams, ...actionParamValues }` (L4704) and resolves templates against it (`resolveCompositeActionTemplate`, L4719-4723) — so `getFromParameters` *can* see a Formik tree exactly as D5 claims. `handleCompositeAction` is at L3598 and `handleCompositeActionInternal` walks `payload.actionSequence` (L3621, loop at L3644). The `[storedRunner.name]` `getFromParameters` precedent is at `RunnerView.tsx:344-347`.
