# 281 — Adversarial review of API-call report section analysis

> Attack of `analysis.md` (issue #281) against the current Miroir codebase. Design *choices* (D1–D16) are not relitigated; feasibility, internal consistency, citation accuracy, missing call sites, and unsatisfiable mechanisms are.

**Verdict.** The analysis accurately describes today’s Spotify example (inline report extractors, Entity-as-display-schema, Spotify-specialized sync, 15-member `reportSection` union, cache/stash behavior) and aligns with #267’s execution path. It is **not implementation-ready as written**: the target render path never names how the browser resolves Endpoint **instances** (easy to wire wrong via `deploymentUuidToReportsEntitiesMapping`), D3 mismatch checks must bind to the **report’s** inline query—not stored Query `371aed0c`, D11 undersells an existing `readonly` prop on `TypedValueObjectEditor`, D15 re-sync action shapes disagree with both `buildCompositeAction` and filesystem `createEntity` upsert semantics, and several closed switches (`reportSectionsFormSchema`, multistep gating) will throw or silently skip unless inventoried.

## Recommendations

- [x] **R1** [blocker] — Browser Endpoint lookup is unspecified and the obvious mapping is wrong: `getReportsAndEntitiesForDeploymentUuid` (`Model.ts:226–276`) exposes only `entities`, `entityVersions`, `availableReports`, `availableQueries` per section — **no endpoints**. `ReportSectionEntityInstance` / `ReportTools.reportSectionsFormSchema` resolve display schema via `deploymentUuidToReportsEntitiesMapping[deploymentUuid][applicationSection].entities` + `findEntityFromUuid` (`ReportTools.ts:79–89`, `ReportSectionViewWithEditor.tsx:187–196`). Endpoint **instances** live under the Endpoint EntityVersion index in the **`model`** section (`useEndpointsOfApplications`, `ReduxHooks.ts:394–420` → `entityEndpointVersion.uuid`; `localCache-redux/.../Model.ts:266–333` → `MetaModel.endpoints`). `getDefaultSpotifyModelEnvironment` also builds `endpointsByUuid` from `defaultSpotifyAppModel.endpoints` (`Spotify.ts:94–100`). → In §5.1 / §5.3, normatively require `useCurrentModelEnvironment(app, map).endpointsByUuid[section.endpointUuid]` or `useCurrentModel(app, map).endpoints.find(e => e.uuid === …)` (and server-side parity via `loadEndpointInstanceFromLocalPersistenceStore`, `DomainController.ts:3222–3247`, hardcoded `"model"` section). Explicitly forbid `deploymentUuidToReportsEntitiesMapping` for HTTP schema resolution.

- [x] **R2** [blocker] — D3 mismatch inputs must be the **report inline query**, not Query `371aed0c`: `ReportViewWithEditor` builds `reportDataQueryBase` from `props.reportDefinition.definition.extractorTemplates` (`ReportViewWithEditor.tsx:118–127`), not from stored Query `spotifyGetPlaylist` (`371aed0c-…`, `Spotify.ts:73`, asset under `e4320b9e-…`). The stored query duplicates the same extractor template JSON but is **not** what the report runner executes. §5.3 step 1 (“extractors / extractorTemplates on the report query”) is correct only if tied to `resolvedQuery` from `useQueryTemplateResults` (`ReportHooks.ts:165–211`), not the Query entity row. → State normatively: mismatch compares `apiCallReportSection` to **`reportDefinition.definition.extractorTemplates`** (after template resolution) or `resolvedQuery.extractors`; document that Query `371aed0c` can drift without affecting the report unless kept in sync manually.

- [x] **R3** [major] — D11 “read-only” already has a first-class prop; no-submit alone is insufficient: `TypedValueObjectEditor` exposes `readonly?: boolean` with comment “no submit button, **no editing**” (`TypedValueObjectEditor.tsx:90–91, L159`) and renders `JzodElementEditor` with `readOnly={true}` (`L556–601`). `ReportInputSection` uses only `displaySubmitButton="noDisplay"` / `useActionButton={false}` (`ReportInputSection.tsx:117–118`) — fields remain editable; OK button mutates URL params. §D11 acknowledges this for input sections but not for the proposed `apiCallReportSection` arm. → Specify `readonly={true}` on the typed payload editor (and document that Formik may still hold mutated values client-side without persistence — product-acceptable for D11, but not “non-editable UI”).

- [x] **R4** [major] — D15 re-sync action shapes vs today’s sync composite: Analysis requires per keyed operation `createEntity` if uuid absent else `updateInstance` (refresh `mlSchema`), and **all** keys (`D15`, §D6.6). `buildCompositeAction` emits at most one `createEntity` via `entity: createdEntities[0]` (`syncExternalServiceSchema.ts:425–434, L577–581`) and never `updateInstance` on Entity rows. Filesystem `createEntity` on an existing uuid **warns** then `upsertInstance(entityEntity.uuid, entity)` (`FileSystemEntityStoreSectionMixin.ts:78–93`) — behavior matches “refresh mlSchema” but via **`createEntity` upsert**, not `updateInstance`. No code path emits multiple entity actions. → Rewrite D15 to match implementable composites: either one `createEntity` upsert per opted-in operation (sequence of model actions) or document `alterEntityAttribute` / Entity upsert; drop `updateInstance` unless you specify instance section (`model` vs meta-model) and payload shape.

- [x] **R5** [major] — D9 “default `scope` to `enabledOperations`” is not implemented: `syncExternalServiceSchemaValue` fails when `scope` is missing or empty (`syncExternalServiceSchema.ts:459–461`). Endpoint `0e5cb172-…` has `enabledOperations: ["get-playlist"]` (`0e5cb172-….json:21–23`) but sync still requires explicit `transformerParams.scope`. Transformer JSON (`c615ff0e-….json:33–40`) documents `scope` optional — contradicts runtime fail-closed. → Add scope defaulting in handler **or** mark D9 as a breaking behavior change in the TDD plan; extend `transformerParameterSchema` with `endpointUuid` (required) and document `operationSync` read from Endpoint instance (D10), not transformer params.

- [x] **R6** [major] — `operationSync` / generalized bounds are greenfield; today bounds are Spotify-only: No `operationSync` in `EndpointExternalService` (`endpointDefinition.ts:39–58`) or endpoint JSON. Bounds come from `DEFAULT_BOUNDED_PATHS["get-playlist"]` (`syncExternalServiceSchema.ts:44–60, L525–526`). Removing constants without shipping `operationSync` on the Endpoint **and** dual-write on Entity `3d8da4d4-…` + EntityVersion `e3c1cc69-…` breaks `get-playlist` sync (analysis D8 says that is intended — but then Spotify example must commit `operationSync.get-playlist.boundPaths` **before** deleting `DEFAULT_BOUNDED_PATHS`). → Sequence dual-write + asset migration in Slice 0; call out `updatedEndpoint` must spread existing `externalService` so `operationSync` survives `operations[]` replacement (`syncExternalServiceSchema.ts:403–411` already spreads — verify `operationSync` is preserved once added).

- [x] **R7** [major] — Closed switches will throw or `{}` unless every arm is updated: `reportSectionsFormSchema` `default` **throws** for unknown types (`ReportTools.ts:111–116`); `jsonReportSection` is not listed (analysis §3.3 correct). `reportSectionsFormValue` returns `{}` for `jsonReportSection` (`L268–273`). **`inputReportSection` also throws** in `reportSectionsFormSchema` (not in analysis). `JsonObjectEditFormDialog` calls `reportSectionsFormSchema` on a report section (`JsonObjectEditFormDialog.tsx:300–311`). → Add `apiCallReportSection` to Entity + EntityVersion unions, bootstrap filter (`getMiroirFundamentalJzodSchema.ts:1582–1601`), **`reportSectionsFormSchema`** (likely `{}` or schema from Endpoint), and **`reportSectionsFormValue`** (seed from `reportData[fetchedDataReference]` per §5.1 — today’s analogue is `objectInstanceReportSection` L179–226, not L180–184 alone).

- [x] **R8** [major] — Multistep report gating ignores unknown section types: `MultistepReportHost.tsx` `collectStepBagKeys` / `currentStepAllowsNext` handle only `inputReportSection` and `objectInstanceReportSection` (`L128–133`, `L254–275`); all other types return `true` for “allows next”. An `apiCallReportSection` in a multistep list will not participate in step validation (likely OK for display-only) but also **won’t** collect bag keys — document non-goal or add explicit arm if multistep + API sections matter later.

- [x] **R9** [major] — D14 Entity deletion blast radius is under-inventoried: Beyond `Spotify.ts:49` / `index.ts:4`, `entitySpotifyPlaylist` is imported in `spotifyApp.integ.test.tsx` (boot assertions, schema checks, L556–703), `externalServiceHttpStoreSkip.unit.test.ts` (`HTTP_ENTITY_UUID = 56166585-…`), `dogfood-sync-spotify-schema.ts`, MiroirTest fixtures expecting `createSpotifyPlaylist` (`f4e5dde0-…`, `394242e7-…`). Deleting the Entity without rewriting tests/fixtures breaks CI. → Expand D14 migration table with test files and dogfood script; keep “Entity-backed HTTP report” fixture in standalone-app as analysis states.

- [x] **R10** [minor] — Union count / container literals: Present-model Report Entity union has **15** members including `openReportSection` (`3f2baa83-….json:1278–1386`); filter list omits `openReportSection` but includes non-union `styledReportSection` — analysis §3.3 correct. Runtime uses container types `"list"` / `"grid"` matching `listReportSection` / `gridReportSection` Zod literals (`miroirFundamentalType.ts:10184–10199`; Spotify report `10ce3252-….json:117` `"type": "list"`). §3.3 “15 members” and grid/list cite (`ReportSectionViewWithEditor.tsx:370, L413`) — correct.

- [x] **R11** [minor] — Transformer param schema vs side-channel params: `c615ff0e-….json` lists only `openApiDocument`, `appModel`, `scope`. Handler reads `transformerParams.endpointUuid` (`syncExternalServiceSchema.ts:475`) and tests pass `entityUuid` in params (`f4e5dde0-….json`). Build-time param evaluation maps **only** keys in `transformerParameterSchema` (`TransformersForRuntime.ts:4101–4121`); runtime handler still receives full `transformerParams` bag for library implementations — feasible, not blocked by Zod `.strict()` on the transformer **node**. → Still add `endpointUuid` to TransformerDefinition JSON (§5.2) for MCP/designer discoverability; do not claim “cannot pass endpointUuid” today.

- [x] **R12** [minor] — Internal consistency: “Query unchanged” vs duplicate extractors: D14 table says Query `371aed0c` “Extractor unchanged” while the report already embeds identical `extractorTemplates` (`10ce3252-….json:10–21` vs `371aed0c-….json:9–20`). Not a runtime bug if understood; wording implies Query drives the report. → Clarify in §3.1 / D14 that the report owns inline extractors; Query is optional parallel asset.

- [x] **R13** [minor] — `ReportViewWithEditor` seeds form values with `defaultMiroirModelEnvironment` (`ReportViewWithEditor.tsx:278`), not the app deployment environment.
