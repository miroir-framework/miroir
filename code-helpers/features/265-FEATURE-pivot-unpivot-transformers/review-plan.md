## Verdict

**Fix-then-ship.** The plan faithfully carries analysis v2 decisions (D1–D10, R1/R3 two-level SQL, R5 applyTo allowlist, R11 `--profile emulatedServer-sql`), paths (`scripts/nonreg-manifest.json`, `docs/reference/transformers.md`, suite UUIDs), and most commands check out. Do not execute as written until three gaps are closed: (1) Slice 1’s row-order assertion cannot pass SQL integration without an explicit `ORDER BY` in D4’s final `jsonb_agg` (Postgres row order is unspecified; comparison is array-order-sensitive via `fast-deep-equal`); (2) Slice 2/3 null/failure leaves omit the suite’s real assertion contract (`retainAttributes` + `unitTestExpectedValue` / `integrationTestExpectedValue`) and unit-mode `unNullify` strips explicit `null` cells; (3) every asset-changing slice omits `modelValidation`, and the selective-run note cites dead `runTransformerTestSuite` API instead of `MIROIR_TEST_FILTER`.

## Recommendations

- [x] **R1** (severity: blocker) — SQL row order will flake against Slice 1 `expectedValue`: Slice 1 asserts pivot output row order “follows first-appearance order” (`tdd-implementation-plan.md:145`) with a fixed array `expectedValue`; comparison uses Vitest `.toEqual` backed by `fast-deep-equal`, which is **array-order-sensitive** (`packages/miroir-core/src/1_core/testing/test-expect.ts:130-131`, `MiroirTransformerTestTools.ts:252-254`, `:505`). Analysis D4 step 7 ends with bare `jsonb_agg` over `GROUP BY row_key` (`analysis.md:91`) with no `ORDER BY`; precedent `sqlStringForSortListTransformer` **does** order: `jsonb_agg(element ORDER BY …)` (`SqlGenerator.ts:3861`). **Fix:** add to Slice 4.2 GREEN (and analysis D4 step 7): propagate input ordinality (e.g. `min(ord)` from the unnest CTE) and emit `jsonb_agg(pivot_row ORDER BY min_ord ASC)` (or `ORDER BY row_key` only if keys are guaranteed sortable and match in-memory order). Re-run Slice 4 validation only after this is specified.

- [x] **R2** (severity: blocker) — Unit-mode explicit `null` cells cannot match current comparison normalization: Slice 2 cycle 2 (`fillValue: null`) and Slice 3 cycle 4 (explicit `null` kept) require `{…, dep1: null}` / `{value: null}` in results. Unit transformer tests normalize **expected** with `unNullify` (null → undefined) then `removeUndefinedProperties` (drops keys), but **actual** keeps JSON `null` (`MiroirTransformerTestTools.ts:222-223`, `:251-252`; `otherTools.ts:50-64`, `:71-84`). SQL integration skips `unNullify` when `runAsSql` (`MiroirTransformerTestTools.ts:87-94`, `:474-477`), so null works there only. **Fix:** for each null leaf, split expectations: `integrationTestExpectedValue` with JSON `null`; `unitTestExpectedValue` omitting null keys (or document unpivot null cases as SQL-only leaves). Do not use a single `expectedValue` for dual-mode null assertions.

- [x] **R3** (severity: major) — Error-case leaves lack a concrete assertion recipe; plan cites wrong lines: Slice 2 cycle 7 and Slice 3 cycle 5 say “check how existing leaves assert failures” (`tdd-implementation-plan.md:198`, `:235`) and Slice 4 cites `MiroirTransformerTestTools.ts:311-319` for failure shape (`:278`) — those lines are **only** the `ansiColumnsToJodSchema` SQL gate, not general failure handling (`MiroirTransformerTestTools.ts:311-319`). Working runtime failure leaves use `retainAttributes: ["queryFailure"]` plus `{ queryFailure: "FailedTransformer" }` (`33f60ac8-…json:4035-4040`, `:3789-3798`) and, when SQL compile/runtime differs, **separate** `unitTestExpectedValue` / `integrationTestExpectedValue` (e.g. `FailedTransformer` vs `QueryNotExecutable` at `:3793-3798`, `:6284-6292`). **Fix:** add a “Failure leaf template” to Slice 2/3 RED: `retainAttributes`, `unitTestExpectedValue: { queryFailure: "FailedTransformer" }`, and `integrationTestExpectedValue` set after Slice 4/5 GREEN once SQL validation timing is known (compile-time `QueryNotExecutable` vs runtime `FailedTransformer` — mirror `plusEmptyArgs`, not `getFromParameters` `:4038-4040`).

- [x] **R4** (severity: major) — Slice 2 and Slice 3 violate skill verticality (one behavior per slice): Skill override 4 requires each slice deliver **one observable behavior** with one RED test (`SKILL.md:56-61`); helper grouping exception applies only to helper-only coverage (`SKILL.md:65-66`). - [x] **R5** (severity: major) — Asset-changing slices omit `modelValidation` (skill checklist item): Plan rebuilds `miroir-test-app_deployment-miroir` in Slices 1–3 (`:153`, `:207`, `:242-244`) but never runs deployment validation.
