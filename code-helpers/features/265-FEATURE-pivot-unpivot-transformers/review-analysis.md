## Verdict

**Fix-then-ship.** The census (45 TransformerDefinition files = 33 real SQL / 6 `"N/A"` / 2 `"TODO"` / 2 missing SQL field / 2 composite), the aggregate wiring template (`4ee5c863-5ade-4706-92bd-1fc2d89c3766`), the cited dispatch line numbers, and the MiroirRight facts all check out against the repo. The adopted product shape (relational pivot/unpivot, existence-boolean default, no `tablefunc`) is also consistent with issue #265. Do not implement from this analysis as written: D4-a’s single `jsonb_object_agg(col_key, value)` cannot implement D5 (`last` is non-deterministic without input order; `count`/`sum`/`min`/`max` need a second aggregation); D3’s `transformer → string[]` contract is incompatible with the cited `getUniqueValues` (returns objects, not strings); and the analysis never specifies how `columns` / `fillValue` compile through `sqlStringForApplyTo`’s 4-type allowlist, `sqlStringForRuntimeTransformer`, `definedContextEntries`, and `extraWith` CTEs — which is the actual SQL machinery. Until those three are rewritten, Goal 3 (SQL parity) and the rights-matrix acceptance scenario are unimplementable as specified.

## Recommendations

- [x] **R1** (severity: blocker) — D4-a cannot implement D5 in SQL: D5 adopts `onDuplicates?: "first" | "last" | "count" | "sum" | "min" | "max"` default `"first"` (analysis D5; issue #265 Interface table). D4-a describes a single pass: “unnest input, group by row key, `jsonb_object_agg(col_key, value)`”. That expression cannot compute `count`/`sum`/`min`/`max` per (row, col); those require `GROUP BY row_key, col_key` with a numeric aggregate *then* `jsonb_object_agg` of the reduced pairs. For `first`/`last`, PostgreSQL 18 docs state `jsonb_object_agg` “produce[s] meaningfully different result values depending on the order of the input values. This ordering is unspecified by default, but can be controlled by writing an `ORDER BY` clause within the aggregate call” (https://www.postgresql.org/docs/18/functions-aggregate.html). The repo never unnests with ordinality: `rg "WITH ORDINALITY|ordinality" packages/miroir-store-postgres` is empty; `sqlStringForSortListTransformer` uses `fct: "jsonb_array_elements"` with no ordinality (`SqlGenerator.ts:3833-3844`). Without `jsonb_array_elements(...) WITH ORDINALITY` (or equivalent), `"last"` is not a deterministic SQL behavior. **Fix:** rewrite D4-a as a two-level plan: (1) unnest `WITH ORDINALITY`; (2) reduce duplicates (`DISTINCT ON (row,col) ORDER BY ord` for first/last, or `GROUP BY row,col` + `COUNT`/`SUM`/`MIN`/`MAX`); (3) `jsonb_object_agg(col, reduced_value)`. Document that existence-boolean mode (`valueAttribute` absent) must ignore `count`/`sum` (those would emit numbers, not booleans) — D5’s claim “rights existence mode unaffected” is false for `count`/`sum`.

- [x] **R2** (severity: blocker) — D3 `columns?: … transformer → string[]` is not what `getUniqueValues` (or a Deployment extractor) returns: Key reuse cites `getUniqueValues` (`handleUniqueTransformer` / `sqlStringForUniqueTransformer`) as “Distinct-key collection (data-derived columns)”. `handleUniqueTransformer` builds a `Set` of attribute values then returns `[...result].map((e) => ({ [transformer.attribute]: e }))` — an array of **objects**, not `string[]` (`TransformersForRuntime.ts:2560-2566`). The SQL handler `jsonb_agg`s the original objects (`SqlGenerator.ts:2385-2401`, alias `"getUniqueValues_objects"`). Issue #265’s acceptance scenario (“`columns` from a Deployment extractor ⇒ matrix of existence booleans”) would feed an array of Deployment **rows** (objects with `uuid`, `name`, …), not `string[]`. Feeding either into a handler that does `for (const col of columns)` would stringify objects into `"[object Object]"` keys. **Fix:** pick one contract and write it into both the analysis and the issue Interface table: (A) `columns` is `string[]` only — Deployment uuids must be plucked first (`mapList` / `accessDynamicPath`); (B) `columns` may be a list of objects plus `columnFromAttribute?: string` (e.g. `"uuid"`); (C) data-derived columns mean “distinct `columnKeyAttribute` values of the **pivot input**”, implemented inside the pivot handler, and `getUniqueValues` is **not** reused as the `columns` argument. Drop the `transformer → string[]` shorthand until the Jzod + runtime resolver match.

- [x] **R3** (severity: blocker) — D4-a + D2 `fillValue` is not specified inside `SqlStringForTransformerElementValue`: Goal 3 and D2 require missing (row, col) pairs to appear with `fillValue`. A single `GROUP BY row_key, jsonb_object_agg(col, value)` only emits keys that exist in the data; filling needs a distinct-column set (from `columns` or `SELECT DISTINCT col`) `CROSS JOIN` distinct rows, `LEFT JOIN` cells, `COALESCE(value, fillValue)`, then re-agg. The SQL element type **can** carry that ( `extraWith?: { name, sql }[]` at `SqlGenerator.ts:247-258`; flattened into the query `WITH` at `SqlGenerator.ts:5812-5817`; `sortList` already appends an unnest CTE at `SqlGenerator.ts:3867-3876`). D4-a never mentions this second pass, never says what `type` the pivot handler returns, and never says how a `columns` transformer’s SQL is attached as a CTE. **Fix:** specify the pivot SQL handler returns `type: "json_array"` (same as `sqlStringForSortListTransformer` at `SqlGenerator.ts:3872-3873`), with `extraWith` CTEs for: applyTo, unnest+ordinality, reduced cells, distinct cols, distinct rows, filled grid, then `jsonb_agg` of `jsonb_build_object(rowKeyAttribute, row_key) || pivoted_object`. If `columns` is omitted, distinct cols come from the cells CTE; if present, resolve it with `sqlStringForRuntimeTransformer` (not `sqlStringForApplyTo`) and unnest that result. `fillValue` becomes a prepared-statement parameter (`$N::jsonb`). Unpivot returns `json_array` of `{...idColumns, nameInto, valueInto}` via `jsonb_each` `LATERAL` (the real precedent is `fct: "jsonb_each"` in `sqlStringForObjectEntriesTransformer` at `SqlGenerator.ts:3668-3676`, **not** the unused `sql_jsonb_each` helper — see R12).

- [x] **R4** (severity: major) — Analysis vs issue Interface drift (`nameInto`/`valueInto`, missing Jzod): Issue #265 Product §1 and the Interface table define unpivot as `{...idColumns, [nameInto], [valueInto]}` with `nameInto` default `"column"` and `valueInto` default `"value"`. Analysis D1/D6/Goals hard-code `{...idColumns, column, value}` and never mention the rename params. The analysis has **no** `transformerParameterSchema` at all; implementers would have to copy the issue table, which itself is TypeScript-ish, not Jzod. Existing optional-transformer params are **not** declared as `string[] | transformer`: `applyTo` and `having` are `"type": "any"` (`aggregate` JSON `4ee5c863-…json:23-27,59-62`; `filterList` JSON `40e894e5-…json:33-36`). Literal-or-transformer **is** used for a **string**, not an array: `createObjectFromPairs` `attributeKey` is `"type": "union", "discriminator": "transformerType"` of `string | schemaReference transformer` (`16d866c4-…json:55-69`). `fillValue?: any` **is** declarable as `"type": "any"` (same as `applyTo`). A union of `string[]` | transformer is **not** the same as `string` | transformer: arrays are JSON objects, so a discriminator-only union can fail to accept a literal `string[]`. The working pattern for primitive/array branches mixed with transformer objects is `optInDiscriminator: true` on `coreTransformerForBuildPlusRuntime` (`getMiroirFundamentalJzodSchema.ts:927-931`). **Fix:** paste a real `transformerParameterSchema` into the analysis: `columns` as either `"type": "any"` (lossy, matches `applyTo`) **or** `"type": "union", "optInDiscriminator": true, "discriminator": "transformerType"` of `{type:"array", definition:{type:"string"}}` | `{type:"schemaReference", relativePath:"transformer"}`; `fillValue` as `"type": "any", "optional": true`; add `nameInto`/`valueInto` to match the issue. Reconcile D1 text with the issue.

- [x] **R5** (severity: major) — `sqlStringForApplyTo` will not compile the rights scenario as a nested pipeline: Issue #265 acceptance is “pivot `MiroirRight` filtered to `targetType = "deployment"`”. `sqlStringForApplyTo` only recurses into `applyTo` when `transformerType` is one of `constantAsExtractor` | `returnValue` | `getFromContext` | `getFromParameters`; anything else (`filterList`, `mapList`, `pivot` itself, …) returns `Domain2ElementFailed("QueryNotExecutable")` (`SqlGenerator.ts:856-879`). Nested `pivot.applyTo = { transformerType: "filterList", … }` is therefore **not** SQL-executable, same as every other list transformer. The working test pattern is `applyTo: { transformerType: "getFromContext", referenceName: "…" }` plus `transformerRuntimeContext` (suite leaf at `33f60ac8-…json:8066-8106`). Issue AC “`sqlStringForApplyTo` extended” only adds `pivot`/`unpivot` to the **outer** parameter union (`SqlGenerator.ts:772-788`); it does not relax the 4-type allowlist. **Fix:** analysis must state: SQL mode requires `applyTo` to be a context/parameter/literal (or omit it for `defaultTransformerInput`); the rights Query is named extractors/combiners (`filteredRights`, `deploymentUuids`) and `pivot.applyTo = getFromContext "filteredRights"`. Add `CoreTransformerForBuildPlusRuntime_pivot | _unpivot` to the `sqlStringForApplyTo` union as the issue AC says.

- [x] **R6** (severity: major) — SQL `columns` as a context-reference transformer is underspecified: `sqlStringForContextReferenceTransformer` looks up `definedContextEntries[referenceName]` and fails with `QueryNotExecutable` if missing (`SqlGenerator.ts:4688-4697`). `SqlContextEntry.type` is only `"json" | "json_array" | "scalar" | "table"` (`SqlGenerator.ts:276-279`) — not `tableOf1JsonColumn`. A combiner/extractor CTE can be `table` (row set) or `json_array`. The analysis never says: (1) `columns` must be resolved with `sqlStringForRuntimeTransformer` (which **can** dispatch nested registered handlers, unlike `sqlStringForApplyTo`); (2) acceptable compiled types (`json_array` of scalars, or `table` plus a pluck); (3) `usedContextEntries` must be forwarded so the WITH-clause assembler keeps the referenced CTE. Reject object-arrays unless R2 option B is adopted. - [x] **R7** (severity: major) — Dense `fillValue` pivot is not the dual of D6 unpivot: D1/D9 call pivot/unpivot duals. D2 writes missing pairs as present keys with `fillValue` (default `false` in existence mode). D6 skips **absent** keys and keeps explicit `null`. After a filled pivot, every column key is present (`false` is not absent), so unpivot emits a row per filled cell — including the synthetic `false`s that were never `MiroirRight` instances. `jsonb_each` matches D6 on a **sparse** object (`SqlGenerator.ts:3668`), not on a dense filled object. Write-back (out of scope) would then create rights for `false` cells unless a later filter exists. **Fix:** state explicitly that fill-dense pivot ∘ unpivot is **not** a round-trip; the sparse dual is pivot with `columns` omitted and `fillValue` unset (missing keys stay missing). Rights-grid queries that need empty checkboxes must fill; unpivot for write-back must filter `value === true` (follow-up, not this issue). Add tests for both modes.

- [x] **R8** (severity: major) — Unpivot collisions and non-JSON cells are unspecified: Issue `idColumns: string[]` are copied onto every output row.
