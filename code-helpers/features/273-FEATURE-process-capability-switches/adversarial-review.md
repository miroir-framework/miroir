# 273 — Adversarial review of process capability switches analysis

> Attack of `analysis.md` (and issue #273) against the current Miroir codebase on branch `273-FEATURE-process-capability-switches`. Design *choices* (D1–D15) are not relitigated; feasibility, internal consistency, and factual claims are. Every citation below was walked against the working tree on 2026-09-12; inventories were verified programmatically.

**Disposition (2026-09-12):** R1–R12 applied in `analysis.md` (D13 uses `hasAccess(..., alwaysAllow: [])` plus `useAuthSession`; Electron keeps D5 capacity and gains a loopback HTTP work item; RestClientStub handler before the auth gate + rest-client fetch; MCP refuse in `runMcpToolRunner` and both `server.ts` mounts; `bundled` excluded from creation; store-admin refuses create/delete/reset only in `handleActionInternal`; `features` read only on the persistence side; citation/inventory/test-blast/timing/exposure notes). Product choices D1–D15 unchanged.

**Verdict (at review time).** The fact base is good: the config inventory (37 files, 0 `features`, 30 `deploymentMode`), all four UUIDs, and nearly every file:line citation check out within ±1, and the core transport bet — wire one handler into `RestClientStub.call` and Electron gets it free via the existing `rest-call` IPC (`ElectronIpcProxy.ts:81-93` → `ipcServerSetup.ts:210-214`) — is sound. But the analysis is **not implementation-ready** as written, for two structural reasons: (1) D13's bulb-visibility check is **vacuous as specified** — `hasAccess` short-circuits on `ALWAYS_ALLOW_APPLICATION_TARGETS`, which contains Admin (`AccessPolicy.ts:36-39`, `:80-82`), so every authenticated user passes "Admin application access" and Goal 4's "non-Admin user with auth on does not see the bulb" cannot happen; (2) D5 + the §5.5 preset row give Electron `ai: true / mcp: true`, but Electron main has **no HTTP server at all** — only IPC (`ipcServerSetup.ts:209-248`) — so the renderer's CopilotKit runtime URL (`AgentsCopilotKit.tsx:28`, relative `/api/copilotkit`) resolves to `app://miroir/api/copilotkit` in prod, where the protocol handler serves `index.html` (`main.ts:60-75`), and MCP runners fetch `window.location.origin` (`runMcpToolRunner.ts:41-46`): enabling the flags lights up UI that is physically unreachable — the exact dead-control bug class this issue exists to eliminate. Several majors compound this: the `RestClientStub` placement is ambiguous relative to the auth gate, the MCP refuse path has no call site, `availableStoreTypes` surfaces read-only `bundled` as a creation backend in the sandbox, the store-admin refusal scope is unspecified (a blanket refusal breaks startup `openStore`), and the Electron/renderer dual-config "required" claim contradicts D12's single-source-of-truth. ## Recommendations

- [x] **R1** [blocker] — D13's "Admin application access" check is vacuous: `hasAccess` returns `true` for **any** authenticated principal when the target is in `alwaysAllow`, and `ALWAYS_ALLOW_APPLICATION_TARGETS` contains Admin (`AccessPolicy.ts:36-39`; the short-circuit is at `:80-82`, after the principal check at `:77-79`). The analysis names "`hasAccess` + `ADMIN_APPLICATION_UUID` (`AccessPolicy.ts:31, 71-88`)" as the bulb check and even quotes the always-allow list in the same paragraph without connecting them. As specified, with auth on, every logged-in user sees the bulb — Goal 4's second sentence ("As a non-Admin user with auth on, I do not see the bulb") is unimplementable from the named mechanism. This is not relitigating D13; it is D13 internally inconsistent with the function it cites. → Specify the exact call: `hasAccess({ principal, target: { targetType: "application", targetUuid: ADMIN_APPLICATION_UUID }, grants, alwaysAllow: [] })` (or a direct grant scan), with `grants` read from the Admin deployment's `MiroirRight` rows in the local cache, and `principal` from the client auth session — `useAuthSession()` (`authSession.ts:89-91`, snapshot carries `principal.miroirUserUuid` at `:12-16`, `:30-47`), a file missing from the analysis's Key sources. Add a test: auth on, Carol (no Admin grant) → no bulb; Alice (Admin grant) → bulb.

- [x] **R2** [blocker] — The Electron preset (`§5.5`: `ai: true`, `mcp: true`) and D5 ("AI/MCP allowed when flags are on") have no transport: Electron main runs **no HTTP listener** — `setupIpcServer` registers only IPC handlers (`ipcServerSetup.ts:205-248`), mounts no CopilotKit route (confirmed §3.3) and no MCP listener. The renderer's `AgentsCopilotKit` uses `runtimeUrl="/api/copilotkit"` (`AgentsCopilotKit.tsx:28`); in prod the window is `app://miroir/home` (`main.ts:171`), so the fetch resolves to `app://miroir/api/copilotkit` and the protocol handler — which serves files from `dist` and falls back to `index.html` for extensionless paths (`main.ts:60-75`) — returns HTML; in dev it hits the Vite server, whose proxy forwards `/api/copilotkit` to a `miroir-server` that is not running (proxy keys pinned in `mcpToolRunner.253.phase0.unit.test.ts:321-329`). MCP runners are worse: `browserMcpServerUrl()` is `window.location.origin` (`runMcpToolRunner.ts:41-46`), same dead end. So the very first Electron run after implementation shows AI icons whose runtime can never answer — precisely what #273 is supposed to prevent. → Pick one and write it down: (a) Electron presets ship `ai: false, mcp: false` until a follow-up issue adds a transport; or (b) this issue includes the transport work item (an express listen in main, or an IPC-shaped CopilotKit/MCP channel next to `rest-call` at `ipcServerSetup.ts:210`). Note the snapshot itself *is* reachable in Electron (R3), so (a) is cheap and honest.

- [x] **R3** [major] — The `RestClientStub` wiring is ambiguous on the one dimension that breaks the feature: placement relative to the **auth gate**. §5.3 says "before `restServerDefaultHandlers`, same early-return style as auth" — but the gate is `assertRequestAllowed` at `RestClientStub.ts:102-113` (auth resolution at `:93-101`), while `restServerDefaultHandlers` dispatch is at `:166-175`; anything between those lines is still gated. D12 says "No auth required", and the startup fetch happens **before login**, so a handler placed after `:113` returns 401 for every auth-on deployment and the client never learns its capabilities. Two more unspecified mechanics: the stub has no snapshot source — it needs a setter mirroring `setIdentityDirectory` / `setAccessDirectory` (`RestClientStub.ts:43-51`) called **after** factory registration in each startup (`server.ts:322-326`, `ipcServerSetup.ts:163-167` + stub creation at `:197-199`, sandbox `index.tsx:119-125` + `:139`, test setups); and the UI fetch must not copy the `/auth/status` pattern of plain `window.fetch` (`index.tsx:377-384`) — in Electron that hits the `app://` protocol handler, not IPC. The capabilities call must go through the environment's `RestClientInterface` (`ElectronRestClient.get`, `ElectronIpcProxy.ts:81-93`), which exists only after `index.tsx:396`. → State explicitly: handler registered before the auth gate in `RestClientStub.call` (sibling of the `handleAuthHttpRoute` block at `:74-91`); a `setProcessCapabilities` injection point; express mount ungated next to `/auth/status` (`server.ts:263-265`); UI fetch via the rest client, after its construction.

- [x] **R4** [major] — The `mcp` refuse path has no call site, and the "off" switch misses half the mounts. UI MCP runners do **not** go through DomainController actions: `RunnerView.tsx:465-469` calls `runMcpToolRunner`, which fetches the MCP HTTP routes directly from the browser (`runMcpToolRunner.ts:23-29` via `callMcpToolViaHttp`). With `mcp` off, the failure is a connection error wrapped as `{ status: "error", error: { type: "FailedToHandleAction" } }` (`runMcpToolRunner.ts:30-37`) — not the D14 `Action2Error` with `errorType: "FeatureUnavailable"` and `errorContext.capability`. Meanwhile D10's "do not start the MCP HTTP server" must gate **two** mounts in `server.ts`: `mcpServer.mountHttpRoutes(app)` (`:823`, the one browser runners actually use via the main origin) and `mcpServer.run(mcpPortFromConfig)` (`:925-926`); gating only the listener leaves `/mcp` alive on the main app. → Name the refuse call site (a snapshot check in `runMcpToolRunner` throwing/returning the D14 shape before fetch) and list both `server.ts` mounts in the D10 work item.

- [x] **R5** [major] — `availableStoreTypes` surfaces `bundled` as a creation backend in the sandbox — the one shape where filtering actually matters. Sandbox startup registers bundled factories including an **admin** factory (`miroir-sandbox/src/index.tsx:119-122`; `miroir-store-bundled/src/startup.ts:54-68`), so the D11 derivation yields `availableStoreTypes = ["bundled", "indexedDb"]` and `storeAdministration = true` (indexedDb admin factory at `miroir-store-indexedDb/src/startup.ts:29`). `storeAdministration: true` in the sandbox is *correct* (IndexedDB creation genuinely works there — the Admin deployment itself runs on it, `miroir-sandbox/src/index.tsx:62-64`), but offering "bundled" in Create Application's backend union (`Runner_CreateApplication.tsx:73-108`) is a dead control: bundled stores are read-only, statically imported (`AGENTS.md` store table; the modelVersion variant is explicitly unsupported, `miroir-store-bundled/src/startup.ts:142-157`). D11's "no per-backend force-off in v1" collides with Goal 1 here. → Add one derivation rule: `bundled` is openable, not creatable — exclude it from creation pickers (or carry a per-type `writable`/`creatable` flag). One sentence in D11 plus the filtered union.

- [x] **R6** [major] — The `storeAdministration` refusal scope and check location are unspecified, and the wrong choice breaks startup. §5.4 refuses "those actions" (create/delete/reset) — but the action family is five: `storeManagementAction_createStore / deleteStore / resetAndInitApplicationDeployment / openStore / closeStore` (`DomainController.ts:3396-3400`). A blanket refusal when `storeAdministration` is false would refuse `openStore` — which every process needs to boot (sandbox opens its deployments via `handleAction` at `miroir-sandbox/src/index.tsx:200-215`; server open loops likewise) — bricking exactly the bundled-only shapes the flag describes. And the check must live in `DomainController.handleActionInternal`'s store-management case, not in `RestServer`: composite actions re-enter via `this.handleAction` (`DomainController.ts:3745-3749`, `:4882-4885` → `:3763`, `:4896`) and in-process MCP tools (`Miroir_storeManagementAction_createStore`, …) call `handleAction` directly; a REST-only check is bypassed by both. → Enumerate the refused actionTypes (create/delete/resetAndInit; never open/close) and pin the check to the DomainController case so REST, composite, and MCP paths share it.

- [x] **R7** [major] — Dual-config drift: D5 says "Adding the flags to **both** objects is required" (renderer `electronMiroirConfig`, `index.tsx:409-432`; main `electronServerConfig`, `ipcServerSetup.ts:172-177`), but under D12 the renderer **never reads its own** `features` — the snapshot is computed in main and fetched. The renderer copy is dead config that can drift (patch one, not the other, and nothing fails loudly — configs are `JSON.parse`d with no schema validation anywhere, e.g. `server.ts:212-216`; `miroirConfig.server.json` doesn't even carry the schema-required `miroirConfigType`). Same for the web client config (`miroir-standalone-app/src/assets/miroirConfig.json`), whose persistence side is the server. Internally, D8's "Patch every repo config" also contradicts §5.5's "Test profiles that never touch AI/MCP can omit the flags and stay false". → State the rule: `features` is read **only** on the persistence side (server config for web, main config for Electron, client config only when `emulateServer: true` — sandbox, in-browser tests); the Electron renderer object does not need it (drop "both … required" or name a reader); reconcile D8 with §5.5 (patch only configs whose shape needs non-default values).

## Suggested decision repairs (not new product choices — consistency of the ones already made)

| Conflict | Repair that preserves the confirmed intent |
|---|---|
| D13 vs `ALWAYS_ALLOW_APPLICATION_TARGETS` | Keep D13; specify `hasAccess(..., alwaysAllow: [])` (or a direct `MiroirRight` grant scan) with the principal from `useAuthSession()` — otherwise "Admin access" is true for every authenticated user. |

| D7/D8 vs dual config | Keep root `features`; state it is read only on the persistence side (client config only when `emulateServer: true`), drop "both objects required" for the Electron renderer, and reconcile "patch every repo config" with §5.5's omit-where-false. |
