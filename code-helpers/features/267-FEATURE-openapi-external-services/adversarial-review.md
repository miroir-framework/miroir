# 267 — Adversarial review of OpenAPI external-services analysis

> Attack of `analysis.md` (and issue #267) against the current Miroir codebase. Design *choices* (D1–D11) are not relitigated; feasibility, internal consistency, and factual claims are.

**Verdict.** The analysis is a coherent product story sitting on a broken execution map. Several cited line numbers and UUIDs check out, and the 11+2 source endpoint inventory is real — but the document asserts mechanisms the code does not have: a report query never enters `DomainController`; application actions never go over `POST /action`; `handleApplicationAction` is void and client-local; server boxed queries die in persistence-store extractor switches; `definition.actions XOR externalService` cannot host the generated `externalServiceCall` actions the sync transformer is specified to upsert. Treat the analysis as **not implementation-ready** until the blockers below are resolved in the analysis itself (then the TDD plan).

**Citation audit (vector A), short:** `DomainController.ts:805`, `:859-869`, `:2943`, `:3042-3055`; `RestServer.ts:55,425,442,510,575,618`; `server.ts:154-191`; `TransformersForRuntime.ts:159,781,3331`; `Model.ts:285-298`; entity UUIDs `3d8da4d4`, `e3c1cc69`, `e4320b9e`, `3f2baa83`, `35961086`, `39e5c7a1`, `cbc94d62`, `212f2784`, `9884c1a4` — all exist. `RestServer.ts:627-658` is sloppy (handlers start at `:623`; `POST /query` is `:656-660`). The “19 test-fixture clones” are **not in the repo**. `instanceEndpointV1` / `instanceEndpointVersionV1` is a second alias of `ed520de4` that the analysis missed.

## Recommendations

- [x] **R1** [blocker] — D1 XOR forbids the actions D2/D6/Goal 5 put on the same endpoint: D1-c makes `definition` `actions` XOR `externalService`. The target design then says the sync transformer “upserts endpoint actions with `externalServiceCall` implementations” onto **that same** endpoint, and Goal 5 / D6 require those actions for composite flows and MCP. MCP `listTools` already **skips** any endpoint without `definition.actions` (`packages/miroir-mcp/src/tools/EndpointToolRegistry.ts:180-187`: `endpoint?.definition?.actions` is the well-formedness test). There is no third place in the analysis for the generated operations to live. **This is not a wording nit — it is an unsatisfiable schema.** → Pick one and write it down: (a) retract XOR and keep `externalService` as a sibling of `actions` (rejected D1-b, but it is what the rest of the design actually implements); (b) XOR stands, generated operations live under `externalService.operations[]`, and MCP / `EndpointActionCaller` / `commandsFromEndpoint` / `handleApplicationAction` read that path instead of `definition.actions`; (c) two endpoint instances (metadata vs actions). Do not ship D1-c plus “upsert actions on the same endpoint.”

- [x] **R2** [blocker] — Report display never hits DomainController; D5 “extractor implies server” is not a real choke point: The Spotify report is specified as URL → query template → `extractorForExternalService` → server fetch. Actual report execution:

  1. `ReportViewWithEditor` builds a query from `extractorTemplates` and calls `useQueryTemplateResults` (`ReportViewWithEditor.tsx:105-140`).
  2. `useQueryTemplateResults` runs **synchronous Redux** `deploymentEntityStateSelectorMap.runQuery` (`ReportHooks.ts:187-192`). That is `QuerySelectors.runQuery` (`QuerySelectors.ts:1078`), which is in-memory and whose `default` branch returns `QueryNotExecutable` (`QuerySelectors.ts:1011-1018`).
  3. Cache fill (`createReportQueryLoadExecutor.ts:184-189`) derives load targets only from extractors with a string `parentUuid` and types `extractorInstancesByEntity` / `extractorByPrimaryKey` (`reportQueryLoadSegment.ts:59-82`). `extractorForExternalService` is skipped; `loadTargets.length === 0` returns without fetching.
  4. Client `DomainController.executeBoxedExtractorOrQueryAction` defaults to `localCacheOrFail` (`DomainController.ts:810-811,890-905`) unless the caller sets `queryExecutionStrategy: "storage"`. ReportHooks never sets that flag. On the **server**, boxed queries always go to `handlePersistenceActionForLocalPersistenceStore` (`DomainController.ts:857-865`) → `PersistenceStoreController.handleBoxedQueryAction` (`PersistenceStoreController.ts:161-192`) → filesystem/SQL extractor runners. Those switches do not know a new extractor type (`AsyncQuerySelectors.ts:422-432`, `SqlGenerator.ts:756-757`, `FileSystemExtractorRunner.ts` `extractorByPrimaryKey` / list cases only).

  D5 cannot be “slightly more dispatch logic” inside `handleBoxedExtractorOrQueryAction`. The UI path **does not call it**. → Specify a report execution mode: detect `extractorForExternalService` in `useQueryTemplateResults` / `ReportViewWithEditor` and `POST /query` (or `handleBoxedExtractorOrQueryAction` with `storage`), then render from the returned context instead of Redux. Document the DomainController **server** intercept **before** the persistence-store handoff (the store cannot inject `MIROIR_SECRET_*`). List every other call site (MCP `compositeRunBoxedQueryAction`, CopilotKit, `QuerySelectors` sync). “Hard error client-side without server” must be implemented at those sites, not wished into the extractor type.

- [x] **R3** [blocker] — `playlistId` is stripped before templates see it; D8 is factually false: Analysis §3.5: “A custom key such as `playlistId` needs no new mechanism.” `PageDispatcher` builds `reportPageParams` as only `application`, `deploymentUuid`, `applicationSection`, `reportUuid`, `instanceUuid` (`PageDispatcher.tsx:99-109`). `ReportUrlParamKeys` is that same closed union (`packages/miroir-standalone-app/src/constants.ts:7-13`). `?page=report&…&playlistId=` never reaches `pageParams` → `getFromParameters`. Legacy path-segment mode (`PageDispatcher.tsx:194-200`) is equally closed. → Forward unknown search params into `pageParams` (or add `playlistId` to the typed keys) **and** still do R2; D8 is not free.

- [x] **R4** [blocker] — `handleApplicationAction` cannot be the server secret-injection point as specified: Secrets are launch-time on `miroir-server`. Dispatch is specified as `DomainController.handleApplicationAction`. Facts:

  1. `handleAction` routes non-Miroir application UUIDs to `handleApplicationAction` **in-process** with no `persistenceStoreAccessMode` remote hop (`DomainController.ts:2919-2928`). `EndpointActionCaller` calls `domainController.handleAction` on the **browser** controller (`EndpointActionCaller.tsx:143-147`). The token is not there; CORS would also kill a browser `fetch` to Spotify.
  2. `POST /action/:actionType` (`RestServer.ts:645-649`) `restActionHandler` switch handles store/model/instance actions only; `default` **throws** (`RestServer.ts:470-474`). `getPlaylist` / `lendDocument` are not REST-routable. Application actions are client-local composite templates today — which is why Lending works without a server secret.
  3. Even if you added a REST case, non-model actions pass `currentModelEnvironment = undefined` (`RestServer.ts:427-434`), and `handleApplicationAction` immediately errors “missing currentModelEnvironment” (`DomainController.ts:2957-2964`). The commented `serverModelEnvironments[action.deploymentUuid]` (`RestServer.ts:358`) was never built.
  4. `handleApplicationAction` is typed `Promise<Action2VoidReturnType>` (`DomainController.ts:2948`). `Action2VoidSuccess.returnedDomainElement` is `void` (`DomainElement.ts:240-266`). D6 “unwraps the `ActionSuccess` payload” has no type to unwrap. MCP already types the result as void (`mcpHandlersForEndpoint.ts:271`).

  → Either: (A) runtime HTTP happens only inside the **server** boxed-query interceptor (R2), and `handleApplicationAction` is an in-process helper on `persistenceStoreAccessMode === "local"`; or (B) add a generic remote application-action transport, pass a per-deployment `MiroirModelEnvironment` resolved from the server store (not `defaultMiroirModelEnvironment`, `RestServer.ts:508,420`), and change the return type to `Action2ReturnType`. Do not pretend today’s `handleApplicationAction` is a server door.

- [x] **R5** [blocker] — D2 “no OpenAPI parsing at runtime” contradicts `externalServiceCall { operationId, parameterMappings }`: D2-a is rejected because it “ships YAML parser + `$ref` resolver to the runtime.” The action shape stores only `operationId`. Target design: `ExternalServiceClient` “builds the request from the stored OpenAPI operation (`GET /playlists/{playlist_id}`)”. Resolving `operationId` → method/path/parameters **is** OpenAPI parse + `$ref` at fetch time, i.e. D2-a. There is no YAML library on `miroir-core` (`packages/miroir-core/package.json`); root `package.json` only *overrides* `"yaml"` — it does not depend on it. Sync is specified to run “client- or server-side,” so D2-d still ships a parser to the Vite client. → Materialize `method`, `path`, `parameters`, `security` onto each generated action at sync time and treat `openApiDocument` as an inert blob at runtime; **or** retract the “no runtime parse” claim and budget a YAML/`$ref` dependency (and do not run that parser in the browser). Pick one.

- [x] **R6** [blocker] — SSRF + credential exfiltration; D6 is not read-only by construction: `ExternalServiceClient` will `fetch(baseUrl + path)` with `Authorization: Bearer <secret[credentialKey]>`. `baseUrl`, `openApiDocument`, `credentialKey`, and `enabledOperations` are ordinary endpoint instance fields. They replicate to every client cache (analysis D1 revisit trigger already admits this). Any principal who can `updateInstance` on that endpoint (REST `RestServer.ts:393-396`, MCP tools generated from InstanceEndpoint, CLI `commandsFromEndpoint.ts:367-370`) can set `baseUrl` to `http://169.254.169.254/` / `http://127.0.0.1:…` / an attacker listener and trigger `extractorForExternalService` or the MCP tool. The server then attaches **whatever secret `credentialKey` names**. Auth default is **on** (`AuthenticationPolicy.ts:80`), so this is a confused-deputy hole for authenticated designers, not only anonymous clients. D6 “runs any data-returning action” plus “read-only by construction — only GET-backed actions exist” is a sync-time wish: nothing stops a hand-written `externalServiceCall` for POST, or `extractorForExternalService` pointing at `lendDocument` / `updateInstance`. QuerySelectors/async runners have no GET-only guard. → Server-side allowlist: HTTPS, deny private/link-local/loopback unless explicitly opted in for the fake test server; pin `operationId` to `enabledOperations`; resolve path only from the **synced** action fields (R5), not from a client-supplied URL; refuse `extractorForExternalService` unless the target implementation is `externalServiceCall` and method is GET; require `credentialKey` to exist and be non-empty before fetch. Document that model write on an external-service endpoint is a privileged operation.

- [x] **R7** [major] — `redactCredentialSecretsFromValue` will not hide the token; logs already dump values the analysis claims are redacted: Implementation (`AuthenticationPolicy.ts:445-462`) walks objects and **deletes `passwordHash`** when `parentUuid === ENTITY_MIROIR_USER_CREDENTIAL_UUID`. It is not value-based and does not know `--secret` / `MIROIR_SECRET_*` values. Call sites the analysis cites (`RestServer.ts:55,425,442,510,575,618`) only run this function. Meanwhile:

  - `server.ts:206` logs `JSON.stringify(process.env)` at startup — every `MIROIR_SECRET_*` lands in the log on the env-fallback path D4 specified.
  - `restActionHandler` logs `result` **before** redaction (`RestServer.ts:435-442`).
  - `handleApplicationAction` logs `JSON.stringify(domainAction)` (`DomainController.ts:2949-2953`); error payload includes `domainAction` (`:3005-3012`).
  - `PersistenceStoreController.handleBoxedQueryAction` logs `JSON.stringify(result)` (`:193-198`); filesystem/SQL query runners do the same (`FileSystemExtractorRunner.ts:135-141`, `SqlDbQueryRunner.ts:509-515`).
  - MCP `handleMcpAction` logs params, constructed action, and `JSON.stringify(result)` (`mcpHandlersForEndpoint.ts:213-277`) with **no** redaction helper at all.
  - MSW/client branch of `restActionHandler` returns `result` **unredacted** (`RestServer.ts:466`).

  Teaching the redactor “the secret values” (analysis D4) is still insufficient: value-based wipe is bypassed by logs, error `innerError` trees, fetch `Authorization` headers in dumped request objects, and MCP. A Spotify 401 body or a mis-logged header is enough. → Do not log `process.env`. Hold secrets in a module-level map that is never JSON.stringified. Redact by **key** (`authorization`, `token`, `credential`, `secret`) and by value. Apply the same helper to MCP and logger formatters, not only `continuationFunction(response)`. Never put the token in query strings. Fail closed if `credentialKey` is missing/empty **before** `fetch`.

- [x] **R8** [major] — `conceptLevel: "External"` and `storageAccess: "none"` do not mean “HTTP, not persisted”: Analysis §3.4 presents postgres `tables`/`columns`/`schemata` as the precedent this issue “extends … to external HTTP.” Those entities have `externalDataSource: { schema: "information_schema" }` (e.g. `35961086-…json:7-21`). Postgres treats `conceptLevel === "External" || externalDataSource` as **a Sequelize model on an external SQL schema** (`SqlDbStoreSection.ts:118-141`) and **skips `CREATE TABLE`** (`:173-175`). A Spotify entity with `conceptLevel: "External"` and no `externalDataSource` still gets `isExternal=true`, `effectiveTableName = entity.name`, and any later `getInstances` is a SELECT against a table that was never created. `storageAccess` is copied into generated schemas and **never read by runtime code** (no `.storageAccess ===` in `packages/**/*.ts` outside schema generation). Feature #208 already recorded this. → Do not reuse `External`+`none` as an HTTP switch. Either ignore those flags for this feature (document that SpotifyPlaylist is a display-schema-only entity, never passed to store boot as a data entity) or add a real discriminant (`externalDataSource.kind: "sql" | "http"`) and teach every store’s `bootFromPersistedState` / `createStorageSpaceForInstancesOfEntity` to skip HTTP entities. Putting this entity in a postgres deployment without that skip will fail at boot or first read.

- [x] **R9** [major] — Discriminated-union refactor is oversold; stored instances have no `definition` tag: Endpoint `definition` today is an **object** with `actions` plus `actionDefinition` / `actionTransformer` / `actionMigrations` (Entity present-model `3d8da4d4-….json:107-118`; EntityVersion `e3c1cc69-….json`). Nested `actionImplementation` already uses `"discriminator": "actionImplementationType"` (`e3c1cc69-….json:200-247`) — the cheap extension is a **third actionImplementation branch**, not XOR of the whole definition (see R1). Jzod does **not** emit `z.discriminatedUnion`: `JzodToZod.ts:983-990` always uses `z.union`, and jzod 0.8.2 release notes say “Zod schema generation for discriminated unions not yet implemented.” Existing instances are `{ definition: { actions: […] } }` with **no** `definitionType` field. A tagged union requires a data migration; an untagged key-XOR (`actions` vs `externalService`) would accept current JSON for the actions branch **if** `.strict()` extra keys are considered — an object with **both** keys fails both strict branches, which is the D1 invariant, and is exactly why D2 cannot upsert `actions` onto an `externalService` instance. Analysis §3.1 also cites only EntityVersion `e3c1cc69`; after #217 the **Entity** present-model `mlSchema` on `3d8da4d4-…` is authoritative and must change too. `getMiroirFundamentalJzodSchema.ts` (e.g. `:2390,2640,2730,2819`) reads `.definition.actions` off hardcoded endpoint JSON to generate `DomainAction` types — every one of those accessors breaks if `definition` becomes a union without narrowing. → If you keep XOR, write the Jzod as untagged union of two objects (no new instance tag), keep `actionDefinition*` on the actions branch, add type guards at every `.definition.actions` reader (MCP, CLI, CopilotKit, `Instance.ts`, `Endpoint.ts`, `commandsFromEndpoint.ts`, `EndpointActionCaller`, `RunnerView`, `resolveMcpToolAction`, bootstrap schema). If you only need `externalServiceCall`, add it to the existing `actionImplementation` union and skip the instance-wide migration.

- [x] **R10** [major] — Extractor taxonomy change is a closed-switch blast; template form is missing: Analysis lists resolved extractor types and a new `extractorForExternalService`. Reports use **`extractorTemplates`**, resolved by `Templates.ts`. That switch’s `default` is `QueryNotExecutable` (`Templates.ts:313-319`). The same closed switches exist in `QuerySelectors.ts:713+`, `AsyncQuerySelectors.ts:164+`, `ExtractorRunnerInMemory.ts:384+`, `FileSystemExtractorRunner.ts:171+`, `SqlGenerator.ts:654+`, `sqlDbInstanceStoreSectionMixin.ts:128+`. Adding a resolved type without `extractorTemplateForExternalService` (bindings as transformers so `getFromParameters` works at resolve time) makes the Report query in §5 unrepresentable. Bootstrap extractor unions live in `getMiroirFundamentalJzodSchema.ts` (`extractorTemplateReturningObject` at `:4116-4132`, etc.) and generated `miroirFundamentalJzodSchema.ts`. → Add **both** template and resolved forms; update every switch; decide SQL `runAsSql` is unsupported (hard error) rather than silently falling into `sqlForExtractor not implemented`.

- [x] **R11** [major] — MCP Goal 5 is a different process with a library-shaped model env and no `--secret`: `packages/miroir-mcp` is its own Node server (`mcp/src/index.ts`). Tools call `domainController.handleAction` in-process (`mcpHandlersForEndpoint.ts:271-274`). `modelEnvironmentOverride ?? getDefaultLibraryModelEnvironmentDEFUNCT` (`:251-255`) — Spotify endpoints are not in the library default env unless `EndpointToolRegistry.callTool`’s cache env (`EndpointToolRegistry.ts:241-256`) actually contains them. `listTools` drops XOR-only endpoints (R1). Secrets CLI is specified only for `miroir-server`. MCP never sees `MIROIR_SECRET_*` unless you duplicate D4 there. Results are logged and returned as tool text (`:277-294`) — playlist JSON is fine; a dumped `Authorization` header is not (R7). → State where MCP runs relative to the secret holder. If MCP is sidecar-to-server with `persistenceStoreAccessMode: "local"`, give it the same `--secret` parser. If it speaks REST, you need R4’s transport. Fix `listTools` for the chosen D1 shape.

- [x] **R12** [major] — `SpotifyPlaylist` identity is undesigned: PlaylistObject uses Spotify `id` (base-62), not a UUID. Entity default PK is `uuid` (`EntityPrimaryKey.ts` / Entity `idAttribute` optional). Report list sections look up `parentUuid` to get the Entity for columns (`ReportSectionListDisplay.tsx:268`). An extractor payload that is a raw PlaylistObject has no `uuid`/`parentUuid`. Non-UUID PK via `idAttribute: "id"` exists and should be stated. Inlining nested `tracks.items[].track.album…` into one `mlSchema` is a large document; combiners expecting instance collections will not see `tracks.items` unless a runtimeTransformer projects them. → Set `idAttribute: "id"` (or wrap the payload into an EntityInstance). Document whether the report is one `objectInstance` section on the root object (nested tracks as JSON) or a list section fed by a transformer. Do not claim “report stack unchanged” without that binding.

- [x] **R13** [major] — Sync transformer `currentModel` is the wrong environment on the server path: Handlers do receive `modelEnvironment: MiroirModelEnvironment` with `currentModel` (`Transformer.ts:13-18`, `TransformersForRuntime.ts` signatures). That part of D2 is feasible **when the caller passes the Spotify deployment’s model**. `POST /query` passes `defaultMiroirModelEnvironment` (`RestServer.ts:508`) — `currentModel` is the **Miroir** meta-model (`Model.ts:126-135`). `FileSystemExtractorRunner.handleBoxedQueryAction` hardcodes the same (`FileSystemExtractorRunner.ts:121`). RestServer still has `TODO: get the right model for the app / deployment` (`RestServer.ts:424,569`). A sync transformer run via the existing query/action REST path will not see the Spotify endpoint/entity instances it is supposed to diff/upsert. `compositeActionSequence` **can** `createEntity` / `updateInstance` (`DomainController.ts:3451-3471`) — that half is real. → Invoke sync with `localCache.currentModelEnvironment(spotifyApplication, map)` (as MCP registry does), never `defaultMiroirModelEnvironment`. If review-then-execute is MCP or a runner, specify that entry point.

- [x] **R14** [major] — HTTP failure modes are unspecified and will be misdiagnosed as schema errors: No behavior for: missing `--secret` / empty value; `credentialKey` not in the map; DNS/TLS failure; non-2xx (Spotify 401 after 1h expiry, 403, 404, 429 — 429 is a listed non-goal but will still happen); empty body; JSON parse error. `fetch` does not throw on 401. Lenient D11 “error on known-field type mismatch” against a `{ error: { status, message } }` body will look like a Jzod failure, not “token expired, restart.” → Map HTTP status to `Action2Error` with a stable `errorType` (`ExternalServiceUnauthorized` / `NotFound` / `UpstreamFailure`) **before** D11. Never validate an error body as `PlaylistObject`. Tests must cover 401 and missing secret, not only 200 fixtures.

- [x] **R15** [major] — OpenAPI→Jzod for `PlaylistObject` is hand-waved: Spotify components use `allOf`, `anyOf`/`oneOf`, `nullable: true` (OAS 3.0), `$ref` cycles (Track ↔ Album ↔ SimplifiedTrack), and `additionalProperties`. Jzod has `jzodIntersection` and `nullable` on elements, but there is **zero** OpenAPI converter in this repo. Discriminators in OAS are not Jzod `discriminator` (and Jzod discriminators do not become Zod discriminated unions — R9). Inlining “nested components” of PlaylistObject pulls PagingObject, PlaylistTrackObject, TrackObject, Artist, Album, Image, Followers, … — the reviewable `compositeActionSequence` JSON will be huge. D11 “strip unknown keys” needs a Jzod→strip implementation that does not exist. → Bound the converted subset (name, owner, tracks.total, tracks.items[].track.{name,artists,duration_ms,id}) instead of “PlaylistObject inlined,” or prototype the converter on the real `open-api-schema.yaml` in the analysis and show the output size. State OAS 3.0 `nullable` → Jzod `nullable: true`, `allOf` → intersection or flatten, and reject `oneOf`/`anyOf` for MVP.

Those 19 files are not a migration set you can PR. Meanwhile `defaultMiroirMetaModel.endpoints` (`Model.ts:285-298`) is 12 **entries** but only **10 unique UUIDs**: `deploymentEndpointV1` and `storeManagementEndpoint` both import `bbd08cbb-….json` (`index.ts:233,241`) — analysis got this — **and** `instanceEndpointV1` / `instanceEndpointVersionV1` both import `ed520de4-….json` (`index.ts:229,234`) — analysis missed it. MenuEndpoint `c6b849a3` is exported and not in the list — analysis got this. Issue #267 still says “migrate the 12 core + library endpoint instances”; analysis says 13 assets. → Migrate the 13 source JSON files + generated types + readers. Do not plan a 19-file fixture hunt. Mention both alias pairs. Test tmp copies are regenerated by tests; if a test asserts exact endpoint JSON, it will fail after D1 and should be named.

- [x] **R17** [major] — Example-app packaging is not “copy Library.ts”: `build-all.sh` stages `miroir-test-app_deployment-library` (e.g. `:81,102,104,664`) and does not know `miroir-test-app_deployment-spotify`. - [x] **R18** [major] — D6 generic `extractorForExternalService` is a mutation side-channel unless constrained: Specified as “runs any data-returning action.” `getInstance`/`getInstances` return data via `handleInstanceAction`, not `handleApplicationAction`, and are not `externalServiceCall`.
