# 286 adversarial review of the React component MiroirTests analysis

> Review of `analysis.md` (issue #286) against the code on branch `286-FEATURE-react-component-miroir-tests`. The decisions D1 to D13 are not reopened. This review checks citations, whether each §5 mechanism can work, missed call sites, internal consistency, and risks that have no mitigation.

**Verdict.** The analysis describes the current test file, the MiroirTest walk, and the UI run path well. The gap list is mostly right. It is not ready to implement. Three points block it. First, the leaf schema change targets the wrong file: `devBuild` generates types from the MiroirTest Entity in `miroir_model/`, not from the EntityVersion the analysis names. Second, React 18.3.1 production builds throw on every `act` call, so RTL cannot run in the production app bundle. Third, `extractValuesFromRenderedElements` searches the whole `document`, and the bodies call it 45 times, so `within(sandboxElement)` does not scope those reads. In addition, the editors' dropdown is a custom `createPortal` to `document.body`, which MUI theme props cannot redirect. The bodies also use more than the §5.3 env object: `container`, `expect.getState()`, and multi-line `screen` chains. Other problems: the vitest naming claim is wrong, the RTL `cleanup()` in `tests/setup.ts` detaches a sandbox appended to `body`, the bare-console guard fails once the tools move under `src/`, and the premise that `test-expect` lacks `toBeNull` and `toBeGreaterThan` is false.

## Recommendations

- [x] **R1** [blocker] — The leaf schema edit targets a file the generator does not read. `generate-ts-types.ts` L394 passes `entityMiroirTest` to `getMiroirFundamentalJzodSchema`, and that function reads `entityDefinitionMiroirTest.mlSchema.definition.definition` (`getMiroirFundamentalJzodSchema.ts` L1467-1471). `miroir-test-app_deployment-miroir/index.ts` L41 binds `entityMiroirTest` to `assets/miroir_model/16dbfe28-…/a311f363-….json`. That Entity file carries its own copy of the schema, with `miroirTestLeaf` at L222. Editing only EntityVersion `51c647fe-…` (§3.3, §5.1, G1) leaves `miroirFundamentalType.ts` unchanged. → In §3.3 and §5.1, name the Entity file `miroir_model/16dbfe28-…/a311f363-….json` as the generator input and require the same edit in EntityVersion `51c647fe-…` (dual write). Add `MiroirTestForReactComponent` and `miroirTestForReactComponent` to the miroir-core `index.ts` export block (L462-473).

- [x] **R2** [blocker] — RTL cannot run in a production build. In `node_modules/react/cjs/react.production.min.js`, `exports.act` is a function that throws `"act(...) is not supported in production builds of React."`. RTL 16 resolves `act` as `React.act ?? ReactDOMTestUtils.act` (`@testing-library/react/dist/act-compat.js` L13), and `render`, `fireEvent`, `waitFor`, and user-event all go through it. The app bundle served from `miroir-server/release/client` is a production build, so every case would fail in the served app. §6 has no risk entry for this. → Add a K entry and a §5.6 rule. Either the sandbox runs only under the Vite dev server (for example `import.meta.env.DEV`) and records every `reactComponentTest` leaf as skipped with an explicit message otherwise, or the analysis names the build that ships React's development `act`. The §7 validation must name which build it runs against.

- [x] **R3** [blocker] — `within(sandboxElement)` does not scope the main value reader. `extractValuesFromRenderedElements` sets `const searchRoot = document` (`JzodElementEditorTestTools.tsx` L1465) and also reads `document.querySelector('[role="listbox"]')` and `document.body` (L1344-1345). It then collects every `input[name]`, `select`, `[role="combobox"]`, and option on the page (L1466-1497, L1766-1806). The active bodies call it 45 times, and 50 `toEqual` checks compare its output. In the app, every named input on the MiroirTest page would enter the result, and the comparisons would fail. G5 and §5.3 cover only `screen`. → Add a gap and a §5.3 rule: `extractValuesFromRenderedElements` takes a required root (`sandboxElement`) and searches only that root plus the sandbox portal container. Add a vitest case with an extra named input outside the sandbox that proves this.

- [x] **R4** [major] — The dropdown portal is not MUI. `ThemedSelectWithPortal` renders its option list with `createPortal(…, document.body)` (`FormComponents.tsx` L695, target L737) and adds `document` listeners (L301, L323). `JzodEnumEditor.tsx` L519 and L534, `JzodLiteralEditor.tsx`, and `JzodElementEditor.tsx` L873 and L1320 use it. The pilot case "renders all enum options" (test L509-566) opens this dropdown and reads its options. MUI `defaultProps.container` (§5.4) reaches only the one `ThemedMUISelect` (`JzodElementEditor.tsx` L1371). For that part, the approach can work on MUI 5.17: v5 `useThemeProps` reads the emotion theme context that the tools' `@emotion/react` `ThemeProvider` sets. That was not checked at runtime. → In G6 and §5.4, add a portal-target context, for example `PortalContainerContext`, that `ThemedSelectWithPortal` reads with `document.body` as the default. The sandbox providers set it to a child of `sandboxElement`. Keep the MUI defaultProps for `ThemedMUISelect`.

- [x] **R5** [major] — The bodies use more than the §5.3 env object. Across the 7 active suites, bodies use `container` 125 times, mostly as the third argument of `extractValuesFromRenderedElements(expect, filter, container, …)`, and the helper reads `container.querySelectorAll` at L1691 and L1705. The Array pilot suite calls `expect.getState().currentTestName` 4 times (test L224-250). The throwing `expect` in §5.5 has no `getState`. Bodies also use the module-level `log`, `formikFieldName`, `testSectionName`, `waitAfterUserInteraction`, and `userEvent.setup()` followed by `user.type` and `user.clear` (26 calls). 17 queries are split as `screen` on one line and `.getAllByRole(…)` or `.getAllByDisplayValue(…)` on the next. The rewrite rule "`screen.X(` becomes `view.X(`" misses those. → Add `container` (the render container) to `ComponentTestEnvironment`. Either give the throwing `expect` a `getState()` that returns `{ currentTestName }` or delete the 4 calls. List the helpers each body imports. Replace the text rule with "every `screen` identifier becomes `view`".

- [x] **R6** [major] — The RTL cleanup in the vitest setup detaches the sandbox. `tests/setup.ts` L41-44 calls `cleanup()` after each test. In RTL, `cleanup` removes every render container whose `parentNode === document.body` (`@testing-library/react/dist/pure.js` L302-313). §5.8 step 2 appends the sandbox element to `document.body` and renders into it, so the first leaf's cleanup detaches it. Later cases then render into a detached node, and `toBeInTheDocument` fails. → In §5.3 and §5.8, render each case into a fresh child `div` of the sandbox element, with the sandbox itself as a non-render wrapper. Otherwise the new entry must opt out of auto cleanup (`@testing-library/react/pure`) and rely on the runner's own unmount.

- [x] **R7** [major] — Moving the tools into `src/` fails a default nonreg guard. `scripts/check_bare_console.py` fails on any unallowlisted `console.log/info/debug/warn/error(` under `packages/*/src`. It runs as the nonreg step `unit-check-bare-console` (`nonreg-manifest.json` L13-20). `JzodElementEditorTestTools.tsx` has 100 `console.log` lines, and bodies log too, for example `"########### ENUM VALUES AFTER CLICK"` (test L553). §3.2 item 6 mentions the logging, but §5.3 does not handle it. → In §5.3, require `MiroirLoggerFactory` loggers in `componentTests/`, or state that `componentTests/` is added to the allowlist in `check_bare_console.py` and in `docs/reference/testing.md` "Bare console.* allowlist".

- [x] **R8** [major] — A second test-mode fork is missing from G7. `JzodElementEditor.tsx` L92-95 sets `isUnderTest` from `import.meta.env.VITE_TEST_MODE` and passes it at L1895. Under test, `JzodElementEditorReactCodeMirror.tsx` L47-53 renders a `<pre>codeMirrorValue:…</pre>` box instead of `ReactCodeMirror`. In the app, the real CodeMirror mounts in every object, array, and any node, hidden with `display: none` (L157). So the §5.4 sentence "the same theme in vitest keeps both runs identical" is false. The effect on role and text queries was not checked. → Add a gap next to G7. Either the sandbox passes `isUnderTest` through a context, as `ProgressiveRenderDisabledContext` does, or the analysis accepts the difference and the pilot checks it.

- [x] **R9** [major] — The matcher inventory is wrong, and `toEqual` semantics change. `test-expect.ts` already has `toBeNull` (L173) and `toBeGreaterThan` (L247), plus `toStrictEqual`, `toBeDefined`, `toBeUndefined`, `toBeNaN`, `toHaveLength`, `toBeGreaterThanOrEqual`, `toBeLessThan`, and `toBeLessThanOrEqual`. §3.1, §3.4, G8, and §5.5 say otherwise. The miroir-core `toEqual` uses `fast-deep-equal` for objects and loose `==` for primitives (L130-131). Vitest `toEqual` ignores keys whose value is `undefined`, and `fast-deep-equal` does not. The 50 active `toEqual` calls switch semantics when the bodies move to the throwing `expect`. → Fix the four sections. Add a §6 risk on `toEqual` drift. In §5.5, either port vitest's undefined-key rule into the throwing `toEqual` or require the pilot to run each case under both libraries.

- [x] **R10** [major] — The vitest names are not `<suite> > <case>`. The walk registers each leaf with `localVitest.test(label, …)` and opens no `describe` for sub-suites (`miroirTestSuiteWalk.ts` L208-236, and there is no `describe` in the file). Vitest names are therefore the bare case label. The label "form state is changed when selection changes" exists in both pilot suites (test L114 and L567), and `-t "JzodObjectEditor"`, as documented in `testing.md` L780-784, no longer matches. → In §5.8, either wrap each sub-suite in `localVitest.describe` in the walk, or have the new entry run one `describe` per sub-suite. Make the consistency test (§5.7) fail on labels reused across suites, not only within a suite.

- [x] **R11** [major] — There is no sandbox host for "Run all", and no filter by leaf type. `RunAllMiroirTestsButton` is rendered by `MiroirTestListDisplay.tsx` (L170, L183), not by `MiroirTestDisplay`, where §5.6 puts `ComponentTestSandbox`. `MiroirTestRunFilter` holds only `testList` and `match` (`miroirTestTypes.ts` L3-6), so "a filter that excludes `reactComponentTest` leaves" cannot be expressed. The button passes `undefined` (L199-210). → In §5.6, name the sandbox host for the list view. Add a leaf-type exclusion, for example `excludeMiroirTestTypes` on the unit execution options checked in the walk, or prune the suite before the run.

- [x] **R12** [major] — The run and the sandbox depend on each other in a loop. `RunMiroirTestSuiteButton.onUnitAction` calls `resetResults()` and then `_runMiroirTestSuite` directly (`RunMiroirTestSuiteButton.tsx` L106-124). No hook lets another component load a chunk or register a runner first. §5.6 renders the sandbox "only when … a run has started", but the runner needs `sandboxElement` before the first leaf. → In §5.6, add a `beforeRun` prop, or a sandbox context the button awaits, that loads the chunk and calls `registerComponentTests`. The sandbox element stays mounted and hidden until then.

- [x] **R13** [major] — The generator step misses the package wiring. Every MiroirTest instance also has a named export in `miroir-test-app_deployment-miroir/index.ts` (L269 onward) and an entry in `defaultMiroirMetaModel.tests` (`src/Model.ts` L351 onward). `tests/modelValidation.unit.test.ts` validates `defaultMiroirMetaModel`. §5.7 writes only the JSON file. How the running app's Miroir store is seeded with MiroirTest rows was not checked. → In §5.7, have the generator also write the export and the `tests` entry, or check that they exist. State how the suite reaches the app's Miroir deployment, then add that to §7.

- [x] **R14** [minor] — The skip semantics are overstated. With `trackActionsBelow = true`, which both the miroir-core entry and the UI buttons use, `_runMiroirTestWithTracking` returns before calling the arm when `leaf.skip` or `parentSkip` is set (`MiroirTestTools.ts` L371-373), and `TestFramework.test.skip` does nothing. §5.2 step 1 therefore never runs on those paths. On the no-runner path, the vitest test body runs and passes, so vitest reports the leaves as passed, not skipped. Only the tracker records "skipped". → In §5.2, say that the no-runner case is skipped in the tracker and passes in vitest, and drop step 1 or mark it as the in-process path only. Put `rethrowComponentTestFailures` on the `"unit"` arm of `MiroirTestExecutionOptions` (L99-110).

- [x] **R15** [minor] — K6 can be closed. `miroir-standalone-app/package.json` L53 already depends on `miroir-test-app_deployment-library`, and `src/miroir-fwk/4-tests/resolveCanonicalTestDeploymentUuid.ts` L3 imports it. `book1` and `entityBook` appear only in the inactive Book and EntityDefinition factories (test L2403-2534). The Country cache helpers are used by #274, not by these suites. → Replace K6 with "resolved: already bundled". Drop the fallback.

- [x] **R16** [minor] — Isolation details. In vitest, one wrapper and one `LocalCache` serve every case of a suite (`getJzodEditorTestSuites`, tools L1223-1227). §5.6 builds one per case, which changes the semantics and reloads the meta-model 68 times. Each wrapper constructs a `MiroirEventService` that starts a 2-minute `setInterval` (`MiroirEventService.ts` L147, L151) and is never destroyed (`destroy()` at L496). In the app that leaks one interval per wrapper. The rest holds: the 7 suites use the `handleAction` stub, so `PersistenceReduxSaga.run`, the module-level `jzodEditorTestLocalCache`, and `DomainController` are not touched. `MiroirContextReactProvider` does not write `MiroirLoggerFactory`. → State per-suite or per-case explicitly in §5.6, and call `miroirEventService.destroy()` on unmount or close.

- [x] **R17** [minor] — The RTL default timeout differs. `tests/setup.ts` sets `configure({ asyncUtilTimeout: 5000 })`. In the browser chunk, RTL keeps its 1000 ms default, so every `waitFor` without an explicit timeout waits 5 times less in the app. K3 says "same timeouts". → In §5.3, have `componentTestEnvironment.ts` call `configure({ asyncUtilTimeout: 5000, testIdAttribute: "data-testid" })` in both runs.

- [x] **R18** [minor] — The re-export and the generator imports. A plain re-export of `getWrapperLoadingLocalCache` drops the per-call `registerTestImplementation({ expect })` that the 14 importers get today (tools L760). The tools also import `emptyObject` from `routes/TransformerBuilderPage.js` (tools L66), which pulls a route page and `TransformerEditor` into the lazy chunk and into the Node generator script. The §5.7 generator imports the registry, so it loads React, MUI, emotion, and every editor under `tsx`. → In §5.3, keep a wrapper `getWrapperLoadingLocalCache` in the tests file that registers and then delegates. Move `emptyObject` to a leaf module. Give the registry a React-free manifest (suite to case labels) that the generator and the consistency test import.

- [x] **R19** [minor] — `.not` on `null`. Test L601 runs `expect(screen.queryByLabelText(/Test Label/)).not.toBeInTheDocument()` with a `null` actual. `test-expect` builds `.not` by inverting the positive matcher (L285-295), so a positive DOM matcher that reads `null.ownerDocument` throws a `TypeError` instead of passing. jest-dom accepts `null` under `.not`. → In §5.5, state that DOM matchers treat `null` as "not in the document" and fail with a message only in the positive form. Add this to the K4 matcher tests.

- [x] **R20** [minor] — Documentation and precedent. §5.9 adds a lazy chunk and a manifest check but does not update `docs/internals/code-splitting.md`, which lists every lazy entry. `FunctionCallTestRegistry.ts` is the existing precedent for "a leaf names a registered TypeScript implementation", and §5.3 does not cite it. → Add both to the §5.9 and §5.3 file lists.
